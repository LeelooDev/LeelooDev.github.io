过去我们使用 AI 编程工具，更多是在对它说："帮我改这个 bug""帮我重构这段代码""帮我写一个功能"。

但 Claude Code 最新推出的 **Dynamic Workflows 动态工作流**，让这个交互方式开始发生变化。

它不只是让 Claude Code 去完成一个任务，而是让 Claude Code 可以根据任务本身，临时设计一套"执行框架"：拆分任务、创建多个子 Agent、并行处理、互相验证、最后合并结果。Anthropic 在 2026 年 6 月 2 日发布的文章《A harness for every task: dynamic workflows in Claude Code》中提到，Claude Code 现在可以"动态编写并编排自己的多 Agent harness"，为当前任务定制专属工作流。

这意味着，AI 编程助手正在从"会写代码的工具"，进一步变成"会组织任务的系统"。

## 什么是 Dynamic Workflows？

简单理解，Dynamic Workflows 就是让 Claude Code 在执行复杂任务时，不再只靠一个上下文窗口一路做到底，而是可以动态生成一套 JavaScript 工作流文件，通过一些特殊函数来创建和协调多个子 Agent。原文提到，这些动态工作流可以执行 JavaScript，并借助特殊函数生成、管理 subagents，同时也支持 JSON、Math、Array 等标准 JavaScript 能力来处理数据。

换句话说，以前你是让一个 AI 角色从头做到尾；现在 Claude Code 可以临时组建一个"小团队"：

有人负责拆解任务；
有人负责执行具体步骤；
有人负责检查结果；
有人负责反驳和验证；
最后再由一个 Agent 汇总输出。

这套机制特别适合复杂、高价值、长流程、需要并行或需要反复验证的任务。

## 为什么需要动态工作流？

普通的 Claude Code 已经能完成很多编码任务，但复杂任务有一个问题：如果所有规划、执行、验证都挤在同一个上下文里，时间一长就容易出错。

Anthropic 在文章中提到，长任务容易出现几类典型问题：比如任务还没完全完成，模型就提前宣布完成；模型偏向相信自己已有的结论；或者在多轮执行后逐渐偏离最初目标。原文将这些问题分别称为 agentic laziness、self-preferential bias 和 goal drift。

这其实非常符合我们平时使用 AI 的感受。

比如你让 AI 做一次大型代码审查，它可能检查了 50 个问题里的 35 个，就给你总结说"已经完成"；
你让它验证自己刚写的代码，它可能天然更倾向于认为自己是对的；
你让它连续处理很多需求，处理到后面，它可能已经忘了最开始你强调过的边界条件。

动态工作流的价值就在这里：它把一个大任务拆成多个独立上下文，让不同子 Agent 各自完成明确目标，再通过结构化方式汇总和验证，从机制上减少这些问题。

## 它不是"更强提示词"，而是"更强执行结构"

很多人使用 AI 时，会把重点放在 Prompt 上，认为只要提示词写得够详细，结果就会稳定。

但 Dynamic Workflows 代表的是另一个方向：不是只优化提示词，而是优化任务执行结构。

比如面对一个复杂问题，不是让 AI 一口气回答，而是让它：

先分类；
再分发给多个 Agent；
每个 Agent 独立处理；
再让验证 Agent 检查；
最后综合成一个结果。

原文总结了几种典型模式，包括 classify-and-act、fan-out-and-synthesize、adversarial verification、generate-and-filter、tournament 和 loop until done。

这些模式非常值得关注，因为它们不只是 Claude Code 的功能点，也可能是未来 AI Agent 产品设计的通用范式。

## 几个最有价值的使用场景

### 1. 大规模重构和迁移

动态工作流很适合处理代码迁移、重构、批量修改等任务。

比如把一个系统里的 User 模型统一改成 Account，普通方式很容易漏掉调用点、测试、文档和边界逻辑。动态工作流则可以把调用点、测试、模块分别拆给不同 Agent 处理，再由另一个 Agent 审查和合并。

原文还提到 Bun 曾使用 workflows 完成从 Zig 到 Rust 的重写相关工作，并建议将任务拆成调用点、失败测试、模块等多个部分，让子 Agent 在独立 worktree 中修复，再由另一个 Agent 做对抗式审查。

### 2. 深度研究

Claude Code 的 Dynamic Workflows 不只适合写代码，也适合研究型任务。

比如你要研究一个技术方案、一个竞品、一个业务问题，动态工作流可以并行搜索资料、抓取来源、验证事实、最后生成带引用的报告。Anthropic 文章中提到，Claude Code 内部发布的 `/deep-research` skill 就使用了动态工作流，会 fan-out 搜索、获取来源、对抗式验证观点，并综合成带引用的报告。

这对于产品经理、开发者、创业者都很有价值。

因为真正复杂的研究，不是"问一次 AI 得一个答案"，而是需要多路径探索、多来源交叉验证、再综合判断。

### 3. 复杂验证

如果你写了一篇技术文章、方案文档、投融资材料，里面有很多事实性判断，普通 AI 很容易顺着你的表达继续写，而不是认真验证每一个事实。

动态工作流可以让一个 Agent 先抽取所有事实声明，再让多个子 Agent 分别验证每条声明，最后再由验证 Agent 判断来源是否可靠。原文也提到，对于需要核查和溯源每个事实声明的报告，可以生成一个 workflow：一个 Agent 识别事实声明，再拆分子 Agent 逐条检查。

这对技术写作、代码审查、合规审查、商业分析都很实用。

### 4. 排序、筛选和评估

动态工作流还适合处理大量候选项的排序。

比如 80 份简历、1000 条用户反馈、几百个 bug report、几十个产品命名方案。普通 AI 一次性处理，很容易因为上下文太长而质量下降。

文章中提到，如果要对 1000+ 行内容进行定性排序，可以使用 tournament、pairwise comparison 或 bucket-rank 等方式，因为比较判断通常比绝对打分更可靠。

这点非常重要。

未来很多 AI 产品，不一定是让模型一次性给分，而是让多个 Agent 分组比较、交叉判断、逐轮筛选，最后得到更稳定的结果。

### 5. 根因分析

对于 bug、事故复盘、销售下滑、数据管道失败这类问题，最怕 AI 只提出一个看似合理的解释，然后沿着这个解释越走越远。

动态工作流可以让多个 Agent 基于不同证据分别提出假设，比如一个看日志、一个看代码、一个看数据，再让验证和反驳 Agent 交叉审查。原文也明确提到，root-cause investigation 可以通过不同 Agent 从分离证据中生成假设，再由验证者和反驳者面板进行检查。

这比单 Agent 线性推理更接近真实团队排查问题的方式。

## 什么时候不该用动态工作流？

动态工作流很强，但不是所有任务都需要。

Anthropic 也提醒，Workflows 仍然是新能力，虽然在很多场景能带来明显收益，但并不适合每个任务，而且可能显著消耗更多 token。对于普通编码任务，没有必要动不动就安排 5 个 reviewer。

我的理解是：

简单任务，用普通 Claude Code 就够了；
复杂任务、长任务、高价值任务、需要多人视角的任务，才适合 Dynamic Workflows。

比如修一个小 UI 样式，不需要动态工作流；
但如果要做一次大型代码迁移、全项目安全审查、复杂事故复盘、竞品研究、业务方案评估，就非常适合。

## 对开发者和产品人的启发

Claude Code 的 Dynamic Workflows 不是一个单纯的"新功能"，它背后其实代表了 AI Agent 的一个重要趋势：

未来的 AI 不只是回答问题，而是会根据任务自动组织执行结构。

过去我们关注的是：
模型聪不聪明？
上下文够不够长？
代码写得准不准？

接下来更重要的问题可能是：
任务怎么拆？
谁来执行？
谁来验证？
什么时候停止？
如何合并结果？
如何控制成本？
如何避免错误扩散？

这也给我们做 AI 产品的人一个启发：很多垂直场景的核心壁垒，可能不只是模型本身，而是"工作流设计"。

比如跨境电商、医疗影像、企业知识库、客户支持、代码审查、数据分析，这些场景真正需要的不是一个聊天框，而是一套能把复杂任务拆解、执行、验证、沉淀的动态系统。

## 总结

Claude Code 的 Dynamic Workflows 让 AI 编程工具向前迈了一步。

它不是简单让 Claude Code "更会写代码"，而是让它更会组织复杂任务：
能拆解，能并行，能验证，能竞争，能循环，能复用。

这也是 AI Agent 从玩具走向生产力工具的关键一步。

未来我们使用 AI，可能不再只是问它一个问题，而是让它为每个复杂任务临时组建一套最合适的执行系统。

这就是 Dynamic Workflows 最值得关注的地方。
