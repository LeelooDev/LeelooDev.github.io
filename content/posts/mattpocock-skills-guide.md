在 TypeScript 社区里，Matt Pocock 是一个绕不开的名字。他是 Total TypeScript 的作者，早年在 Stately 参与 XState 状态机的开发，这几年几乎以一己之力把"TS 教育"做成了一个品类。2025 年之后他把重心转向了 AI 工程，做了 AI Hero，开始研究一个很具体的问题：怎么让 AI 编程助手像资深工程师一样工作，而不只是像一个手速很快的实习生。

[mattpocock/skills](https://github.com/mattpocock/skills) 就是这个问题的答案。这个仓库很不寻常：它是开源项目，但里面几乎没有可运行的代码。二十多个目录，每个目录的核心是一份 `SKILL.md`——一份写给 AI 看的操作手册。有的教 AI 在动手前怎么把需求问清楚，有的规定了测试驱动开发的红绿循环该怎么走，有的定义了调试一个疑难 bug 时的完整纪律。

换句话说，Matt Pocock 把自己带团队、写代码、做架构的工程习惯，全部封装成了 AI 可以反复执行的 SOP。这篇文章讲清楚三件事：这套东西的运作机制、怎么装怎么用，以及——很少有人写的——多套技能并存时会踩什么坑。

## Skills 到底是什么

要理解这个仓库，得先理解 Agent Skills 这个机制本身。

Claude Code、Codex 这类 AI 编程代理都支持一种扩展方式：在约定目录下放一份 `SKILL.md` 文件，文件头部是一段 YAML 元数据（名字、描述、触发方式），正文是给 AI 的详细指令。它的加载方式是渐进式的：

- **描述常驻**。每个技能的一句话描述会一直待在 AI 的上下文里，让它知道"我有这个工具"。这部分很便宜，通常每个技能只占几十个 token。
- **正文按需加载**。只有当任务真正匹配时，完整的操作手册才会被读进上下文。

这个设计决定了 Skills 和我们熟悉的 `CLAUDE.md` 的分工：`CLAUDE.md` 是常驻的全局约定（项目用什么框架、代码风格是什么），Skills 是按需展开的专项流程（遇到 bug 该走什么调试循环）。前者回答"这个项目是什么样的"，后者回答"这类任务该怎么做"。

Skills 还分两种触发方式，这个区别在实际使用中非常关键：

- **用户触发型**：你主动输入 `/grill-me`、`/to-spec` 这样的命令才会启动。这类技能通常是一整套交互流程，AI 不会自作主张地开启。
- **模型触发型**：技能描述里写明了适用场景，AI 判断任务匹配时自动采用。比如你说"帮我调试这个报错"，`diagnosing-bugs` 技能就会自己介入。

理解了这两种类型，你就能读懂这个仓库的设计意图：需要人类参与决策的环节（需求访谈、规格确认）做成用户触发，纯执行纪律的环节（TDD、调试循环、合并冲突）做成模型触发。人管方向，纪律管过程。

## 仓库全景：二十多份 SOP 的地图

仓库把技能分成 engineering 和 productivity 两大类，但按用途看，其实是四组，对应软件开发的四个阶段：

| 阶段 | 技能 | 解决什么问题 |
|---|---|---|
| 需求对齐 | `/grill-me`、`/grill-with-docs`、`grilling` | 动手前连环追问，暴露没想清楚的需求 |
| 规格与拆解 | `/to-spec`、`/to-tickets`、`/triage`、`/wayfinder` | 把讨论固化成规格，拆成带依赖关系的任务 |
| 实施与质量 | `/implement`、`tdd`、`code-review`、`diagnosing-bugs`、`prototype` | 按规格实施，测试先行，出问题走调试纪律 |
| 上下文管理 | `/handoff`、`domain-modeling`、`writing-for-agents`、`research` | 跨会话交接、沉淀领域词汇、管理 AI 的"知识" |

还有一个特殊的 `/ask-matt`：当你不知道该用哪个技能时，它负责把你路由到正确的那一个。

注意第四组。前三组在别的技能仓库里也能找到对应物，但"上下文管理"这一组是这个仓库最有辨识度的部分——它假设你和 AI 的协作是长期的、跨会话的，所以需要专门的机制来沉淀共识。后面深读技能时会回到这一点。

## 安装与初始化

安装有三种方式，取舍很清楚：

**方式一：Claude Code 插件（推荐）**。整套安装、自动更新、统一管理：

```bash
claude plugin marketplace add mattpocock/skills
claude plugin install mattpocock-skills@mattpocock
```

装完后重启会话，或用 `/reload-plugins` 热加载。所有技能会带上 `mattpocock-skills:` 命名空间前缀。

**方式二：npx 挑选安装**。适合 Codex 等其他代理，或者只想要其中几个技能：

```bash
npx skills@latest add mattpocock/skills
```

安装器会列出全部技能让你勾选，装到项目或全局目录，之后文件归你，可以随意改。

**方式三：直接拷贝**。把仓库 clone 下来，挑 `skills/` 目录里的文件复制到自己的技能目录。最原始，但最可控。

装到哪一级也值得想一下：装到 user 级（全局）意味着所有项目共享这套工作流；装到 project 级则只对单个仓库生效。如果你还在观望，先在一个项目里试；确认合手再提到全局。

装好之后还有关键一步：**在每个要使用的项目里跑一次 `/setup-matt-pocock-skills`**。它会问你这个项目用什么方式跟踪 issue、triage 标签怎么设、文档放在哪里。这不是走过场——`/to-tickets` 要往哪里写任务、`/triage` 按什么标签流转、领域模型文档落在哪个路径，全靠这一步的配置。跳过它，一半技能会处于"能跑但不知道往哪使劲"的状态。

## 核心工作流：一条主线走完一个需求

单个技能只是零件，这套仓库真正的产品是一条完整的流水线。做一个新功能的标准走法是：

```
/grill-me → /to-spec → /to-tickets → /implement → /handoff
```

值得逐步看一下每一环防的是哪种翻车。

**`/grill-me`：防"方向性翻车"。** 这是作者建议"每次都用"的技能。你描述想做的东西，AI 不写代码，而是连环追问：这个功能给谁用？失败路径是什么？为什么不用现成方案？边界条件呢？AI 编程最贵的错误从来不是语法错误，而是它十分钟生成八百行代码、但从第一行就理解错了需求。追问阶段每多花一分钟，返工阶段就少烧十分钟的 token。

**`/to-spec`：防"共识蒸发"。** 追问结束后，这一步把整场对话固化成一份可追踪的规格文档。没有这一步，你和 AI 达成的所有共识只存在于当前会话的上下文里——上下文一满、会话一关，共识就蒸发了。

**`/to-tickets`：防"步子太大"。** 把规格拆成带依赖关系的小任务，而且拆法有讲究：每个任务是一颗"曳光弹"（tracer bullet）——一条纵向打穿的最小完整路径，而不是横向铺开的一层。先让一发子弹飞出去看弹道，再决定后面怎么打。

**`/implement`：防"裸奔实施"。** 按任务实施，内部自动驱动 TDD 循环和代码审查。注意它不是一个"更努力写代码"的提示词，而是一个流程容器：写失败测试、最小实现、过审查，一环扣一环。

**`/handoff`：防"上下文断崖"。** 长任务做到一半上下文快满了怎么办？这一步把当前会话的关键状态——做了什么、为什么这么做、还剩什么——压缩成一份交接文档，让下一个会话（或另一个 AI）无损接力。

这条流水线背后的判断是：AI 编程的瓶颈已经不在"写代码"这一环了，而在写代码之前的对齐和之后的延续。五个环节里只有一个环节真正在写代码，这个比例本身就是这套方法论的立场。

## 深读两个技能：克制与野心

全景看完了，值得把两个技能拆开看细节——一个代表这套仓库的克制，一个代表它的野心。

### `/tdd`：38 行的纪律

打开 TDD 技能的 `SKILL.md`，第一个意外是它只有 38 行左右的正文。但这 38 行的密度很高：

- **测试边界（seam）先行确认**：测试只写在公共边界上，而且写之前要和用户确认边界在哪——不是闷头追求覆盖率；
- **红绿循环**：先写失败测试，每轮只加让测试通过的最小实现；
- **循环中禁止重构**：重构留给之后的 code review 阶段，一次只做一件事；
- **三个点名的反模式**：与实现耦合的测试、同义反复的断言（测试只是把实现抄了一遍）、横向切片（一上来铺一大片测试）。

这份手册几乎没有一句废话，也几乎没有给 AI 留下自由发挥的空间。这是写给 AI 的文档和写给人的文档的本质区别：给人的文档要解释为什么，给 AI 的 SOP 要压缩到只剩怎么做。规则越短、越无歧义，执行就越稳定。

### `domain-modeling` + `CONTEXT.md`：作者自认最酷的技术

Matt Pocock 在 README 里说，领域模型是"整个仓库里最酷的一项技术"。机制是：通过 `/grill-with-docs` 的访谈，把项目的领域词汇——这个系统里"订单"到底指什么、"发布"和"上线"是不是一回事——沉淀进一份 `CONTEXT.md`，此后所有会话都基于这套共享语言工作。

为什么这件事值得"最酷"的评价？因为它解决的是 AI 协作里最隐蔽的成本：**每个新会话都要重新解释一遍项目**。没有共享词汇时，你每次都在用自然语言重新描述同一批概念，AI 每次都在重新猜测你的意思，词不达意的偏差在长对话里不断累积。有了领域模型，一个术语顶过去一段解释——省 token 只是表层收益，深层收益是 AI 的输出在跨会话之间保持一致。

这也是理解整个仓库的钥匙：它不把 AI 当一次性工具，而是当一个需要"入职培训"的长期协作者。`CONTEXT.md` 就是它的入职手册，而且会随着每次访谈持续更新。

## 避坑与取舍：多套技能并存的真实问题

这部分是大多数介绍文章不写、但你一定会遇到的。

我装这套技能之前，环境里已经有两套同类的技能集。表面上看是"能力叠加"，实际发生的是三件事：

**模型触发变得不可预测。** 三套技能里各有一个 TDD、各有一个调试流程，描述都写着"遇到 bug 必须用我"。AI 每次都要在几个近似技能里挑一个，今天走这套循环、明天走那套，行为一致性反而下降了。技能的价值恰恰在于"每次都一样"，并存直接消解了这个价值。

**上下文被描述占满。** 前面说过每个技能的描述常驻上下文。一个技能几十 token 不算什么，三套七八十个技能加起来，就是几千 token 的固定开销——AI 还没开始干活，先要读完一整页"工具说明书目录"。

**命令撞名。** Claude Code 自带 `/code-review`，这套仓库也有一个 `code-review`。直接输 `/code-review` 走的是内置版（查 bug 和效率问题），想用 mattpocock 版要输全名 `/mattpocock-skills:code-review`。两者其实互补——内置版查"代码对不对"，mattpocock 版查"代码符不符合本仓库规范、符不符合 spec"——但你得知道撞名这回事，否则永远只会触发其中一个。

所以我的做法是先做减法再做加法：把职能重合的那套整个卸载，再装这套。如果你的环境也已经有同类技能，建议同样处理——**技能列表越精简，触发越准**。留下的重合项（比如我保留的另一套里也有 TDD），用一两周观察实际触发情况，再决定禁用哪边。

还有一个降低预期的提醒：这套技能的工作流假设你愿意在写代码之前花时间对齐。如果你的使用习惯是"一句话让 AI 出结果"，`/grill-me` 的连环追问会让你觉得烦。它值不值，取决于你做的事情返工成本高不高——一次性脚本用不上它，长期维护的项目里它每一分钟都花在刀刃上。

## 结语：Prompt 优化的是这一次，Skills 固化的是每一次

回到开头的问题：Matt Pocock 为什么不做一个更强的 AI 工具，而是写了二十多份操作手册？

因为他赌的方向是：模型能力会持续变强，但"能力强"和"工作可靠"之间隔着一层东西——工程纪律。资深工程师和普通工程师用的是同一门语言、同一个编辑器，差别在于前者有一套稳定的工作方法：先问清楚再动手，测试先行，调试有章法，交接有文档。这套方法过去只能靠人与人之间的言传身教，现在可以写成 `SKILL.md`，让 AI 每一次都严格执行。

这就是 Skills 和 Prompt 的本质区别。Prompt 是一次性的：这一次你说得好，这一次结果就好。Skills 是制度性的：把"怎么做"固化下来，让每一次都按同样的标准发生。前者依赖你的临场发挥，后者把你最好的一次临场发挥变成了默认值。

装不装这套技能，可以再想。但它背后的这个动作——把你自己的工程习惯写成 AI 可执行的 SOP——值得每个和 AI 长期协作的工程师抄走。
