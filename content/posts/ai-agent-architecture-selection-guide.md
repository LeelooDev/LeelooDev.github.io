> 一个刚做完的 Agent demo，很像一艘装饰到极致的巨轮：模型、工具、记忆、规划、反思、子 Agent、向量数据库和 Graph 全部装上了，第一眼极其壮观。真正的问题却在水线以下——它能不能稳定向前，出了故障会不会沉，以及有没有人知道该在哪里刹车。

Agent 项目最常见的错误，不是模型选错了，而是**把所有看起来先进的模式放进同一套系统，却没有先回答“流程到底由谁控制”**。

有人把 Workflow、ReAct、Plan-and-Execute、Reflection、Supervisor 和 LangGraph 并列成六种架构；有人刚写出一次工具调用，就开始设计五个 Agent 的组织结构；还有人把一条本来能用三段代码跑完的流程画成复杂状态图，最后连自己都无法解释一次请求为什么走到了某个节点。

这篇文章试着把这些概念重新放回正确的位置。目标不是再背一遍模式名，而是建立一套能直接用于技术选型的判断方法：**什么应该写死，什么可以交给模型；什么时候需要计划，什么时候需要多 Agent；以及从 demo 到生产，中间究竟还缺哪些工程层。**

## 一、先纠正分类：这些概念根本不在同一层

“Agent 架构”经常被讲成一排互相竞争的选项，但它实际至少包含四层问题：

```text
第一层：控制流——下一步由谁决定？
├─ Workflow：代码预先规定路径
└─ Agent：模型根据当前状态决定下一步

第二层：单 Agent 推理——一个循环内部怎样推进？
├─ ReAct
├─ Plan-and-Execute
└─ Reflection

第三层：多 Agent 协作——多个角色怎样交换任务和结果？
├─ Supervisor / Hierarchical
├─ Pipeline / Handoff
├─ Network / Blackboard
└─ Debate

第四层：实现——怎样表达状态、节点和转移？
└─ Graph / State Machine / 普通代码
```

这四层可以自由组合，并不互斥。

一个系统可以用 Graph 实现固定 Workflow，也可以用 Graph 实现 ReAct 循环；一个 Supervisor 可以管理多个 ReAct worker，也可以只调度几个没有自主决策能力的普通函数；一个 Agent 内部可以先 Plan，再用 ReAct 执行，测试失败时进入 Reflection。

所以真正的架构讨论不该是“ReAct 和 LangGraph 选哪个”，而应该是：

1. 哪些转移必须由代码控制？
2. 哪些局部决策需要模型根据环境反馈动态完成？
3. 状态是否需要持久化、回放和人工介入？
4. 任务是否真的需要多个独立上下文？

只要这四个问题没有回答，框架选型就只是提前采购家具，却还没有画房子的承重结构。

## 二、第一道分界线：Workflow 还是 Agent

[Anthropic 在 Building Effective Agents 中](https://www.anthropic.com/engineering/building-effective-agents)给出了一个很实用的区分：Workflow 通过预先定义的代码路径编排模型和工具；Agent 则由模型动态决定自己的过程和工具使用。[LangGraph 的官方指南](https://docs.langchain.com/oss/python/langgraph/workflows-agents)也沿用了相同边界。

| 形态 | 谁决定下一步 | 适合什么 | 主要代价 |
| --- | --- | --- | --- |
| 单次调用 | 代码 | 摘要、分类、改写、结构化提取 | 无法处理中间反馈 |
| Workflow | 代码 | 路径可预知、规则明确、需要审计的任务 | 难覆盖未预设的变化 |
| Agent | 模型 | 需要探索、调用工具并根据结果持续调整的任务 | 成本、时延和行为更难预测 |

这个区分非常重要，因为很多产品其实不需要 Agent。

“把一份录音转写、提取行动项、按模板生成纪要、最后检查格式”是一条稳定的 Workflow。模型参与了每一步，但它没有必要决定下一步该做什么。“去仓库里找到登录偶发失败的原因并修复”则不同：模型必须先搜索代码，再根据结果决定读哪些文件、运行什么测试、是否修改计划，这才需要 Agent。

判断时可以问一个简单问题：

> 如果把输入类型列出来，我能否提前画出绝大多数合法路径？

如果答案是“能”，优先使用 Workflow；如果环境反馈会不断改变后续动作，而且无法提前枚举，才让模型接管局部控制流。

### Workflow 的五种基本积木

Workflow 并不等于一条僵硬的直线。常见模式已经足以覆盖大量业务：

| 模式 | 结构 | 典型场景 |
| --- | --- | --- |
| Prompt Chaining | A → 校验 → B → C | 翻译后润色、提取后生成 |
| Routing | 分类 → 专用分支 | 客服分流、模型分层调用 |
| Parallelization | 多路并发 → 汇总 | 多维审查、独立章节处理 |
| Orchestrator-Workers | 动态拆分 → 多 worker → 合成 | 文件数量未知的批量修改、研究报告 |
| Evaluator-Optimizer | 生成 → 评估 → 带反馈重试 | 有清晰质量标准的内容和代码任务 |

这五种模式里已经包含“动态拆分”和“反复优化”，因此看到多个模型调用，不代表系统就是多 Agent；看到模型参与路由，也不代表整个控制权都交给了模型。

复杂度应该像权限一样按需授予。能用一次调用解决，就不要上 Workflow；能用 Workflow 解决，就不要让 Agent 自由探索。

## 三、Agent 的内核其实很小：ReAct 循环

剥掉产品界面和框架抽象，一个工具型 Agent 的核心并不神秘：

```text
while 未完成且预算未耗尽:
    模型读取目标、历史与工具定义
    模型输出文本或工具调用
    系统校验权限和参数
    系统执行工具
    工具结果写回上下文
```

[Claude Agent SDK 对 agent loop 的说明](https://code.claude.com/docs/en/agent-sdk/agent-loop)也是同一结构：模型评估当前状态、请求工具、接收工具结果，然后重复，直到返回不再包含工具调用的最终消息。

这就是 ReAct 的工程形态：Reason 与 Act 并不是要求模型把思维过程打印出来，而是让“判断—行动—观察”形成闭环。

ReAct 适合处理环境反馈密集的任务。搜索结果可能为空，编译器可能报出新的错误，网页结构可能和预期不同；每一步都需要根据真实观察调整下一步。在这些场景里，先写死完整路径往往比让模型逐步决策更脆弱。

但 ReAct 也有三项天然成本：

- **每一步都会增加上下文**：工具定义、参数和返回结果会持续累积。
- **局部决策容易失去全局方向**：模型可能在一个失败点附近反复尝试。
- **结束条件具有主观性**：模型可能过早宣布完成，也可能迟迟不停。

因此一个可上线的 ReAct 循环，至少还需要最大轮次、时间和 token 预算、重复调用检测、权限系统、取消机制，以及独立于模型自述的完成校验。循环很小，可靠运行循环的外壳才是主要工程量。

## 四、Plan 不是另一套架构，而是 ReAct 的方向盘

Plan-and-Execute 的基本想法是先列出完整计划，再逐项执行。它解决了 ReAct 容易只顾眼前的问题：

```text
目标
  ↓
生成计划：步骤、依赖、验收标准
  ↓
按计划执行
  ↓
汇总结果
```

在依赖关系稳定的任务里，这种方式非常有效。计划可以给人审查，可以提前识别并行项，执行阶段也能交给更便宜的模型或确定性代码。

问题在于，Agent 面对的环境通常不是静态试卷。第三步的工具结果可能直接推翻第一步的假设。如果计划被当成不可修改的命令，中间错误会一路传导；如果每次变化都整体重规划，又会增加大量延迟和 token。

更实用的做法是 **Plan + ReAct**：

1. 任务开始时生成一份简短计划，记录目标、步骤和验收标准。
2. 进入 ReAct 循环，计划只作为方向锚点，不是不可修改的脚本。
3. 每完成一项就更新状态，而不是重新生成整份计划。
4. 新观察改变前提时，只修改受影响的步骤。
5. 最后按验收标准逐条验证，而不是由模型凭感觉宣布完成。

计划最重要的作用不是预测未来，而是让系统随时知道：**现在做到哪里、为什么在做、怎样才算结束。**

### Reflection 也必须接在客观信号上

Reflection 常被描述成“让模型反思自己的回答”，这很容易退化成昂贵的自我评价。真正有效的 Reflection 通常有一个外部裁判：

- 代码任务看测试、编译器和静态检查结果；
- 数据任务看 Schema、约束和对账结果；
- 检索任务看引用能否回到原文；
- 浏览器任务看页面状态是否真的变化；
- 运维任务看健康检查和监控指标。

于是 Reflection 不再是“你再想想”，而是：

```text
执行 → 客观验证失败 → 读取错误证据 → 修复 → 再验证
```

如果任务没有可判断的反馈，增加反思轮次往往只会让模型更流畅地重复自己。

## 五、2026 年更实用的默认组合

生产系统很少只用一个模式。更常见的做法，是让确定性代码负责边界，让模型只负责那些确实需要语义判断的局部。

### 组合一：Plan + ReAct + Verification

这是编码、研究和运维 Agent 最稳妥的默认结构：

```text
计划 → ReAct 执行 → 测试/校验 → 必要时局部修复 → 完成
```

计划防止目标漂移，ReAct 处理现场变化，Verification 截断错误传播。三者不是重复功能，而是分别回答“往哪走”“下一步怎么走”“到底走到了没有”。

### 组合二：Router + Workflow + Agent

知识问答和客服产品更适合分层升级：

```text
请求
├─ 简单且规则明确 → 固定 Workflow
├─ 需要多轮检索   → 单 Agent
└─ 高风险或证据不足 → 人工处理
```

大部分请求走成本和时延可预测的路径，只有少数复杂问题获得更多自主性。不要让所有流量都进入最昂贵的 Agent 循环。

### 组合三：Orchestrator + 并行 Workers

深度研究、大规模代码审查和批量迁移，往往可以按来源、目录、模块或评价维度拆开。Orchestrator 负责生成任务书，workers 在独立上下文中并行执行，最后由合成器汇总。

这个模式的价值不只是提速。独立上下文能避免主会话被大量搜索过程和工具输出淹没，也能让审查者不受生成者的思路影响。

但并行必须建立在子任务真正独立的前提上。如果多个 worker 同时修改同一份状态，最后付出的冲突协调成本可能高于节省的时间。

### 组合四：Evaluator-Optimizer

写作、翻译、结构化报告和部分代码生成任务，往往不需要多个有长期状态的 Agent。一个生成调用、一个独立评估调用，加上最多两三轮的带反馈修订，就已经足够。

这里最关键的是停止条件。评估者必须根据具体 rubric 判定，而不是笼统说“还可以更好”；重试必须有上限，否则两个模型很容易在风格偏好上无限拉扯。

## 六、Graph 是实现层，不是复杂系统的入场券

Graph 的价值，是把状态和转移显式化：节点可以是模型调用、工具、普通函数或人工审批；边可以是固定连接，也可以根据程序规则或模型输出选择。

同一套 Graph 可以表示完全不同的系统：

```text
固定 Workflow： A → B → C

ReAct：         Model ↔ Tools

带人工审批：    Generate → Review → Approve / Reject

Supervisor：            ┌→ Worker A ─┐
                Manager ├→ Worker B ─┼→ Synthesize
                        └→ Worker C ─┘
```

当系统需要持久化、断点恢复、人在环、长任务暂停、复杂条件分支和完整回放时，LangGraph 一类状态图框架很有价值。它把原本散落在回调和 `if/else` 中的控制流变成可以观察的系统结构。

但 Graph 不会自动让一个糟糕的 Agent 变可靠。工具契约仍然含糊、完成标准仍然不存在、失败仍然被吞掉时，把它们画成图只是得到一张更漂亮的故障地图。

项目早期先用普通代码写出最小循环，常常是更好的学习路径。等到状态管理和恢复需求真实出现，再迁移到 Graph，届时每个节点和边为什么存在都已经有证据，而不是来自框架示例。

## 七、多 Agent 的价值不在“角色扮演”

多 Agent 最容易制造一种错觉：给模型起不同名字，就等于获得了不同专家。实际上，如果所有角色使用同一模型、相似提示词、共享全部上下文，它们很可能带着相同偏见得出相似结论，只是额外消耗了更多 token。

多 Agent 真正有价值的地方主要有两个：

1. **并行性**：任务可以拆成相互独立的部分，同时执行确实能缩短总时间。
2. **上下文隔离**：不同子任务或审查角色需要干净上下文，主会话也容纳不下全部过程。

常见协作拓扑各有明确边界：

| 拓扑 | 控制方式 | 适合 | 风险 |
| --- | --- | --- | --- |
| Supervisor | 中心角色派发和汇总 | 任务拆解、代码审查、研究 | 中心瓶颈与转述损耗 |
| Pipeline | A 完成交给 B | 固定内容生产、数据处理 | 上游错误向下游传播 |
| Handoff | 当前角色移交控制权 | 客服专家分流、分阶段协作 | 控制流分散，难以预测 |
| Network | Agent 自主选择下一个角色 | 探索性研究 | 难审计、难终止 |
| Blackboard | 通过共享状态协作 | 松耦合专家系统 | 并发一致性和收敛问题 |
| Debate | 对立观点与裁判 | 高价值评审的最后一关 | 成本高，容易发散 |

[OpenAI Agents SDK 的 handoff](https://openai.github.io/openai-agents-python/handoffs/)把移交实现为模型可调用的工具，并允许对交接输入做 Schema 约束和过滤。这揭示了多 Agent 工程的本质：**不是让角色自由聊天，而是设计一套清楚的交接协议。**

每个子 Agent 至少应该收到一份包含目标、范围、禁止事项和验收标准的任务书；返回值应该有固定结构；系统还要规定最多打回几轮、超限后由谁接管。传递可验证的产物，不要依赖含糊的自然语言转述。

## 八、从架构图到生产，中间还缺四层

选出控制流和协作模式，只是完成了骨架。真正让 Agent 能上线的，是下面四层看起来不那么“智能”的工程。

### 1. 工具契约：让模型没有猜参数的空间

工具描述要像一份严格接口文档：什么时候调用、什么时候禁止调用、每个参数从哪里获得、返回哪些状态。参数能用枚举就不用自由字符串，ID 必须来自真实查询结果，所有调用在执行前再次做权限和语义校验。

工具失败后不要静默兜底。把结构化错误返回给模型，它才有机会换查询、改参数或选择其他路径。对删除、部署、支付等有副作用的操作，还需要幂等键、dry-run、人工确认和执行后校验。

工具层的完整设计方法，我在[《从零学会企业级 AI Agent 开发（二）：工具层实战》](/posts/enterprise-ai-agent-02)里做了更细的拆解。

### 2. 记忆与上下文：不要把一切都塞进对话

上下文窗口不是数据库。系统提示、工具定义、历史消息和工具输出会持续占用空间，长任务最终一定需要压缩和外部工作区。

短期状态至少要保留四件事：当前目标、已做决策、正在执行的步骤、未完成项。详细搜索结果和中间文档应该写入 scratchpad 文件，需要时再读回。跨会话记忆则要经过提取、合并去重、存储和按需检索，不能把每次对话摘要原样堆进向量库。

[Claude Agent SDK 的上下文指南](https://code.claude.com/docs/en/agent-sdk/agent-loop#the-context-window)特别提醒，大型工具输出会迅速消耗上下文；自动压缩也可能丢失早期细节，因此持久规则和关键状态必须有独立载体。

### 3. 失败恢复：先分类，再决定是否重试

网络抖动、限流和偶发超时属于瞬时故障，可以在幂等前提下有限重试；参数错误、权限不足和服务配置错误属于持久故障，重复三十次也不会变好；本来就需要十分钟的构建则不是故障，应该设计成异步任务。

每个工具要有自己的超时，整个任务还要有总预算。写操作超时尤其不能盲目重试——“没有收到成功响应”不等于“没有执行成功”。重试前先查最终状态，或者从一开始就使用幂等键。

### 4. 权限与安全：外部内容只是数据，不是指令

Agent 读到的网页、邮件、代码注释和工具返回都可能包含提示词注入。权限系统不能指望模型自行判断一段话是否恶意，而要从能力边界上限制影响：只挂当前任务需要的工具、默认只读、敏感操作单独批准、机密与外部内容隔离、所有副作用留审计记录。

模型负责提出动作，系统负责决定动作能不能发生。这条边界不能反过来。

## 九、评估 Agent：答案对了，不代表系统做对了

传统聊天产品经常只评最终回答。Agent 还必须评估过程，因为它可能选错工具、违反权限、绕远路，最后碰巧得到一个看起来正确的结果。

一套完整评估至少分三层：

| 层级 | 看什么 | 适合的判定方式 |
| --- | --- | --- |
| 单步 | 工具选择、参数、单步产物 | Schema、断言、规则代码 |
| 轨迹 | 是否循环、是否漏步骤、恢复路径是否合理 | 轨迹规则 + LLM rubric |
| 终态 | 任务是否完成，副作用是否正确 | 测试、数据库状态、人工标注 |

能用程序判断的部分，不要交给 LLM-as-Judge。JSON 能否解析、参数是否存在、测试是否通过、文件是否真的修改，都应该由确定性代码负责。只有路径合理性、写作质量这类难以形式化的维度，才使用模型裁判，而且要逐项给 rubric。

[Langfuse 的代码评估器文档](https://langfuse.com/docs/evaluation/evaluation-methods/code-evaluators)给出的例子也集中在这些确定性检查：JSON 合法性、工具参数、业务规则，以及不同 prompt 或模型配置间的可重复实验。

最先应该建立的不是公开 benchmark，而是一组来自真实使用的回归案例。把每次踩过的坑变成永久测试：错误参数、空检索、工具超时、需要拒答的问题、权限不足、任务中途取消。每次换模型、改提示词、增加工具都重新跑一遍。

没有回归集的 Agent 优化，很容易只是把错误从一个案例搬到另一个案例。

## 十、一张真正能用的选型表

最后把判断压缩成一张表：

| 你的任务 | 起点 | 什么时候升级 |
| --- | --- | --- |
| 一次生成就能完成 | 单次调用 | 输出需要分步校验时上 Workflow |
| 步骤固定、规则明确 | Prompt Chain / Routing | 路径无法提前枚举时上 Agent |
| 需要连续观察环境 | ReAct 单 Agent | 长任务失去方向时加入可更新 Plan |
| 有客观成败信号 | ReAct + Verification | 失败需要自动修复时加入 Reflection |
| 复杂分支、暂停恢复、人在环 | Graph | 状态管理成为真实负担时再引入 |
| 子任务可并行或上下文装不下 | Orchestrator + Workers | 先证明拆分收益高于协调成本 |
| 专家接管整个会话 | Handoff | 为交接数据增加 Schema 和过滤 |
| 高风险结论需要多视角 | 独立评审 / Debate | 只放在最后把关，不贯穿全流程 |

如果仍然拿不准，可以按这个顺序实施：

1. 定义可以被验证的任务完成标准。
2. 用裸 API 写一个只接一两个只读工具的最小 ReAct 循环。
3. 加入参数校验、权限、错误回传、预算和取消。
4. 用真实案例建立回归集与完整 tracing。
5. 长任务再增加计划、工作文件和压缩。
6. 出现持久化和复杂恢复需求后再上 Graph。
7. 最后才为并行性或上下文隔离拆分多 Agent。

## 结语：不是装得越多，船就开得越远

Agent 架构最迷人的地方，是我们似乎可以不断给系统增加新的“认知器官”：规划、反思、记忆、角色、辩论、图编排。可生产系统的质量从来不取决于名词数量，而取决于边界是否清楚。

哪些路径必须写死，哪些决策允许模型动态完成；工具从哪里获得真实参数，失败怎样暴露；状态存在哪里，预算耗尽时如何停下；最终由什么证据证明任务完成——这些问题全部回答之后，框架通常只是实现细节。

真正成熟的 Agent，不是看起来最自主的那个，而是**在该自主的地方有空间，在不该自主的地方有护栏；遇到变化能调整，遇到错误会停下，完成之后拿得出证据。**

那时它才不只是一艘开幕式上鲜花满载的巨轮，而是一套真的知道如何穿过风浪、抵达目的地的系统。
