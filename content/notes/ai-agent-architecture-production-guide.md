做 AI Agent 最容易走偏的地方，是一上来就讨论框架、模型和多智能体。真正决定系统能不能上线的，通常是三个更基础的问题：**流程由谁决定、失败怎样恢复、结果如何验证。**

这份笔记把 Agent 工程拆成控制流、推理策略、协作拓扑和实现层四个维度，再给出一套从原型走向生产的落地顺序。核心原则只有一句：**先用最小复杂度形成可靠闭环，再为已经出现的瓶颈增加自主性。**

## 先建立一张架构地图

“Agent 架构”不是一个平铺的模式清单。Workflow、ReAct、Supervisor 和 Graph 分属不同层级，不能放在一起比较。

```text
控制流：流程由谁决定？
├─ Workflow：代码预先规定路径
└─ Agent：模型根据环境反馈决定下一步

单 Agent 推理策略：一次循环内部怎样推进？
├─ ReAct
├─ Plan-and-Execute
└─ Reflection

多 Agent 协作拓扑：多个角色怎样交换任务和结果？
├─ Supervisor / Hierarchical
├─ Pipeline / Handoff
├─ Network / Blackboard
└─ Debate

实现层：怎样把状态、节点和转移落到代码？
└─ Graph / State Machine
```

这张图解决了两个常见误区：Graph 是实现控制流的方式，不是与 ReAct 并列的一种思考策略；Supervisor 是多 Agent 的组织结构，也不等于所有复杂任务都必须使用多个 Agent。

## Workflow 与 Agent 的边界

[Anthropic 对有效 Agent 的总结](https://www.anthropic.com/research/building-effective-agents)区分了 workflow 与 agent：前者由代码编排模型和工具，后者让模型动态决定过程和工具使用。

| 方案 | 谁决定下一步 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| 单次模型调用 | 代码 | 最简单、延迟和成本最低 | 无法处理中间反馈 |
| Workflow | 代码 | 可预测、可测试、易审计 | 只能覆盖预先设计的路径 |
| Agent | 模型 | 能根据环境变化调整步骤 | 成本、时延和行为更难预测 |

Workflow 常见的五种组合方式如下：

- **Prompt Chaining**：固定步骤串联，例如提取、校验、润色。
- **Routing**：先分类，再进入专门分支。
- **Parallelization**：把独立部分并发处理，或让多个结果投票。
- **Orchestrator-Workers**：由编排者动态拆分任务，再汇总 worker 结果。
- **Evaluator-Optimizer**：生成、评估、带反馈重试，直到满足标准或达到上限。

选择顺序应当是：**单次调用 → Workflow → 单 Agent → 多 Agent**。只有当前一层无法满足任务要求时，才进入下一层。自主性不是免费的能力，它会同时扩大状态空间、故障面和评测成本。

## 单 Agent 的三种推理策略

### ReAct：默认执行循环

ReAct 可以概括为“判断 → 行动 → 观察 → 再判断”。模型每一步都根据最新工具结果决定下一步，因此非常适合编码、搜索、运维和交互式排障。

它的优势是灵活、容易起步、能就地纠错；问题是长任务会不断扩张上下文，模型可能重复尝试、局部打转，成本也随步数上升。生产系统必须配套步数上限、工具预算、循环检测和取消机制。

### Plan-and-Execute：提供全局方向

先生成计划，再逐项执行，适合步骤较多且依赖关系相对清楚的任务。计划便于人工检查，也能帮助系统识别可并行步骤。

但计划不应成为不可修改的脚本。现实环境会反馈新信息，任何一步都可能推翻原假设。如果每次异常都重新生成整份计划，成本和延迟反而可能高于 ReAct。

更实用的组合是 **Plan + ReAct**：计划作为持续更新的任务清单，ReAct 负责实际执行；完成一项就更新状态，发现前提变化就局部修改计划。计划提供方向，循环保留纠偏能力。

### Reflection：只在有客观信号时使用

Reflection 让模型检查失败并再次尝试。在测试、编译、Schema 校验、规则检查等存在客观信号的任务上，它很有效：

```text
修改代码 → 运行测试 → 读取失败信息 → 定位原因 → 修复 → 再验证
```

如果没有可验证标准，仅让模型“反思一下”，往往只是增加调用次数。最可靠的反思材料来自环境，而不是模型对自己输出的主观评价。

## 生产系统更适合组合模式

单一模式很少能覆盖完整产品，以下四种组合更值得作为工程默认值。

| 场景 | 推荐组合 | 为什么 |
| --- | --- | --- |
| 编码、研究、运维 | Plan + ReAct + 客观验证 | 同时保留全局方向和现场纠偏 |
| 企业问答、客服 | Router + 固定 Workflow + 复杂任务升级 Agent | 大部分请求走便宜且稳定的路径 |
| 内容生产 | Prompt Chain + Evaluator | 流程明确，质量标准可重复执行 |
| 深度研究、大规模审计 | Orchestrator + 并行 ReAct Workers | 子任务可以并行，且能隔离上下文 |

多 Agent 只有两个充分理由：**任务可以真正并行拆解，或单个上下文无法容纳完成任务所需的信息。** 如果只是想让一个角色写、另一个角色审，先尝试 Evaluator-Optimizer workflow，通常更简单，也更容易复现问题。

## 工具调用：可靠性来自契约

模型会编造参数，通常不是因为“它不够聪明”，而是工具契约留下了猜测空间。生产工具应该像给新同事使用的 API：参数从哪里来、允许哪些值、失败后怎么办，都要明确。

按优先级可以建立七道防线：

1. **使用严格 Schema**：让结构化输出从生成阶段就受类型约束。
2. **缩小参数空间**：能用枚举就不用自由字符串；ID 增加格式限制，数值设置上下界。
3. **写清工具描述**：说明调用时机、禁用场景，以及参数必须来自哪个查询结果。
4. **控制可见工具数量**：合并功能重叠的工具，低频工具按需加载。
5. **运行时再次校验**：检查资源是否存在、权限是否满足、参数语义是否正确。
6. **把错误原样返回给 Agent**：不要静默修正或吞掉错误，让模型基于真实环境恢复。
7. **为危险操作增加幂等、预演和确认**：支付、删除、部署等动作不能依赖模型自觉。

Schema 合法不等于语义正确。模型完全可能生成格式正确但不存在的 `user_id`，所以“约束生成 + 运行时校验 + 明确错误反馈”必须形成闭环。

## 记忆：先解决管理，再选择存储

记忆分为会话内的短期记忆和跨会话的长期记忆。

| 类型 | 内容 | 常用实现 |
| --- | --- | --- |
| 短期记忆 | 当前目标、最近观察、待办和中间结果 | 上下文窗口、摘要、工作文件 |
| 语义记忆 | 用户偏好、项目事实 | 结构化档案、键值存储 |
| 情景记忆 | 过去发生过的任务和事件 | 时间线、事件记录、向量索引 |
| 程序记忆 | 已验证的做事方法 | 规则文件、Skills、操作手册 |

长任务不要只依赖上下文窗口。接近容量上限时，应把历史压缩成包含**目标、关键决策、当前状态和未完成项**的摘要；详细的调研结果、计划和中间产物则写入工作文件，需要时再读取。

长期记忆的标准流水线是：

```text
extract → consolidate → store → retrieve
提取        合并去重      保存      按需取回
```

其中最难的是 `consolidate`。如果只提取不合并，记忆库会充满重复、冲突和过期信息，再好的向量数据库也无法补救。项目早期优先使用人可读、可版本管理的 Markdown；只有记忆规模和检索需求被真实数据证明后，再引入向量索引或知识图谱。

## 多 Agent：协议比角色名称重要

以“写代码 + 审查”为例，只有当审查者需要独立上下文，或代码量超过单个上下文承载能力时，才值得拆成两个 Agent：

```text
Supervisor
├─ Coder：接收任务书，产出 diff、说明和测试结果
└─ Reviewer：只接收 diff 与验收标准，独立给出结构化意见

Supervisor：通过 / 带意见打回 / 超过轮次后升级人工
```

多 Agent 系统至少需要三份明确契约：

- **任务书**：目标、允许修改的范围、禁止事项和验收标准。
- **产物格式**：上游必须返回哪些字段，下游如何判断结果完整。
- **终止条件**：最多尝试或打回多少轮，何时转人工处理。

上下文隔离是多 Agent 的价值来源之一。审查者如果完整看到写作者的推理过程，很容易继承相同假设；应传递可验证的产物和约束，不必传递全部思考过程。同时要警惕 Supervisor 的转述损耗，关键要求应该随任务书原文传递。

## 超时和失败：先判断故障类型

不是所有失败都应该重试。

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 瞬时故障 | 网络抖动、限流、偶发超时 | 有上限的指数退避与随机抖动 |
| 持久故障 | 参数错误、权限不足、服务配置错误 | 停止重试，换路径或上报 |
| 慢任务 | 构建、批量分析、大查询 | 提交异步任务，返回任务 ID 后轮询 |

每个工具需要独立超时，整个任务还需要总时间和成本预算。读操作通常可以安全重试；写操作必须先确认幂等性。一次支付请求超时，不代表它没有执行，盲目重试可能制造重复副作用。

重试用尽后，应把结构化错误交给 Agent，让它决定更换工具、降级方案或如实告知用户。服务连续失败时再启用断路器，避免每个任务重复消耗相同的无效重试。

## 评估：不仅看答案，还要看过程和终态

Agent 可能用错误工具、绕远路甚至违反约束，最后碰巧得到正确答案。因此评估至少分三层：

1. **单步评估**：工具是否选对，参数是否正确，单步产物是否相关。
2. **轨迹评估**：是否出现循环、是否超过预算、关键检查点有没有执行、失败恢复路径是否合理。
3. **端到端评估**：任务是否完成，以及外部系统最终状态是否符合预期。

LLM-as-Judge 适合评估表达质量或复杂轨迹，但必须使用逐项 rubric，避免只问“这个结果好不好”。能够用代码断言、测试、数据库终态或人工标注判断的部分，优先采用确定性评估。

落地时先从真实失败案例建立一组 30–100 条回归用例。每次修改提示词、模型、工具或工作流都重新运行，再逐步增加 tracing、线上完成率、人工接管率、平均步数、成本、延迟和工具失败率。公开基准能帮助理解模型能力，但自己的真实问题集才是产品质量的主要依据。

## 最常见的十个坑

1. **过早拆成多 Agent**：单 Agent 尚未调通，就先增加通信和调度复杂度。
2. **上下文无限膨胀**：没有摘要、工作文件和关键状态持久化。
3. **错误逐步放大**：关键节点缺少程序校验，后续步骤建立在错误前提上。
4. **无限循环**：没有步数、成本、重复调用和打回轮次上限。
5. **静默失败**：工具错误被吞掉，Agent 基于不存在的成功继续推理。
6. **提示词回归**：为一个案例修提示词，却没有回归集检查其他场景。
7. **工具幻觉**：工具描述和参数约束不足，模型只能猜。
8. **只验证 Demo**：没有覆盖脏数据、超时、并发、取消和权限边界。
9. **成本失控**：所有步骤都使用大模型，任务也没有 token 与时间预算。
10. **忽视提示词注入**：把网页、文档和工具返回误当成可信指令。

## 一套可执行的落地顺序

如果从零开始，可以按下面的顺序推进：

1. 用单次调用验证任务价值，定义一个可判断的成功标准。
2. 用裸 API 写最小 ReAct 循环，只接入一两个只读工具。
3. 增加严格 Schema、运行时校验、错误回传、超时和步数上限。
4. 用真实失败案例建立回归集，并记录完整执行轨迹。
5. 长任务加入可更新计划、工作文件和上下文压缩。
6. 只有出现明确的持久化、人在环或复杂分支需求时，再引入 Graph 框架。
7. 只有任务确实可并行，或需要独立上下文时，再拆分多 Agent。
8. 上线前验证权限、幂等、取消、降级、成本预算和提示词注入边界。

最终目标不是让系统看起来更像一个“自主智能体”，而是让它在真实环境里**知道什么时候行动、怎样从失败中恢复、何时停止，以及如何证明自己确实完成了任务。**
