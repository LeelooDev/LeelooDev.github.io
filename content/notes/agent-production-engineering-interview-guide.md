这 22 道题考的不是“会不会调用模型 API”，而是能不能把一个概率性组件放进确定性的生产系统。一个成熟答案应始终围绕四个词展开：**有界、隔离、可恢复、可观测**。

- **有界**：并发、队列、上下文、重试、步骤、耗时和成本都必须有上限。
- **隔离**：租户、会话、故障域、资源池和第三方依赖不能互相扩散影响。
- **可恢复**：写操作幂等，长任务有检查点，失败能降级、续跑或补偿。
- **可观测**：能从一次用户请求下钻到模型、检索、工具和队列中的每一步。

回答这类问题时，最好先用一句话给结论，再展开故障机制、工程方案、观测指标和取舍。下面的每题都按这个思路组织。

## 1. 本地 Demo 能跑通，生产并发一高 Agent 就 panic，核心原因是什么？

**面试结论：Demo 只验证了单请求的功能正确性，高并发暴露的是并发安全、资源容量和异常路径问题；panic 是结果，不是根因。**

最常见的根因有四类：

1. **共享可变状态没有隔离或同步**：把会话历史、工具结果、当前用户、缓存容器放在全局对象中；多个请求同时修改同一个 Map、List、Client 或状态机。Go 中可能直接出现 `concurrent map read and map write`，其他语言也会表现为数据错乱、空指针或偶现崩溃。
2. **资源使用无上限**：每个请求无限创建 goroutine、线程或异步任务，没有信号量和背压；连接池、文件描述符、HTTP 连接、内存或下游配额耗尽后，代码仍按“资源一定可用”的假设继续执行。
3. **错误和取消路径没有被正确处理**：超时后对象已经释放，后台任务仍在回写；同一个 Channel 被关闭两次；对空结果、错误类型断言或部分响应未做检查；流式请求断开后没有把取消信号传到检索、模型和工具层。
4. **依赖或 SDK 的线程安全假设错误**：复用了不可并发使用的会话、解析器或流对象；连接池配置与生产并发不匹配；失败重试又放大了瞬时流量。

排查不能只在入口加 `recover`。`recover` 最多防止单个请求拖垮进程，真正的定位步骤是：

- 保留完整 panic 栈、`trace_id`、`run_id`、并发量和资源水位。
- 用与生产相同的连接池、超时、数据规模做阶梯压测和持续压测。
- 打开 race detector、线程或 goroutine dump、CPU/Heap Profile，观察崩溃前的对象和任务数量。
- 检查每个共享对象的所有权：是请求级、会话级、进程级，还是租户级；请求状态默认必须是请求级。
- 给并发、队列、连接池和重试加硬上限，并在达到上限时排队、降级或拒绝，而不是继续申请资源。

一句加分回答是：**生产稳定性不是靠捕获 panic，而是靠消灭无界资源、共享状态和未定义的生命周期。**

## 2. Agent 服务最常见的生产环境内存泄漏有哪些？如何排查和修复？

**面试结论：先区分“真正无法回收的对象”“队列或会话的合法堆积”“内存碎片或运行时未归还 OS”，再根据对象增长路径修复；只靠定时重启不是解决方案。**

常见问题包括：

| 类型 | 典型表现 | 修复方向 |
| --- | --- | --- |
| 会话与上下文无界增长 | 全量保存每轮消息、推理轨迹和工具大结果 | 滚动窗口、结构化摘要、外部对象存储、TTL 和容量上限 |
| 缓存无界增长 | 高基数 Key、没有 TTL/LRU、模型版本变化后旧缓存不淘汰 | 最大条目数/字节数、TTL、版本化 Key、淘汰策略 |
| 异步任务或协程泄漏 | 请求结束后任务仍等待 Channel、锁、网络或定时器 | 传播取消、设置超时、关闭任务组、回收定时器和监听器 |
| 网络和文件资源泄漏 | Response Body、流、Socket、文件、数据库游标未关闭 | `finally/defer/with` 统一释放；连接池指标和泄漏检测 |
| 回调与引用链泄漏 | 事件订阅未注销，闭包长期引用完整请求上下文 | 解除订阅、缩小闭包捕获对象、明确生命周期 |
| 大对象和重复拷贝 | 整份文档、JSON、Embedding、图片在多步骤反复复制 | 流式处理、分块、零拷贝或引用对象存储中的产物 |
| 原生/GPU 内存未释放 | Python Heap 正常但 RSS 或显存持续涨 | 检查原生库、Tensor 生命周期、显存缓存和进程隔离 |
| 队列积压伪装成泄漏 | 到达速率长期大于处理速率，内存中的 Job 越来越多 | 有界队列、背压、扩容、降级；不要按普通 Heap 泄漏处理 |

排查要建立“基线—复现—对比”的闭环：

1. 同时看 RSS、Heap In-use、对象数、GC 次数与停顿、队列深度、活跃任务、连接池和会话数。
2. 做持续压测：流量停止并完成几轮 GC 后，活对象是否回到稳定水位。回不去才更像真正泄漏。
3. 在相同负载的两个时间点做 Heap Snapshot 差分，按类型和分配栈找持续增长对象，再沿引用链查是谁持有它。
4. 将 `tenant_id/session_id/run_id` 作为诊断维度，但不要直接放进高基数监控标签；详细关联放在 Trace 或日志中。
5. 修复后做长时间 Soak Test，验证 Heap 平台期、GC 和吞吐，而不只是“短测不 OOM”。

语言工具可分别使用 Go `pprof`、Java Heap Dump/JFR、Python `tracemalloc`/对象引用分析、Node.js Heap Snapshot。工程上最有效的规则是：**缓存、会话、队列、任务、工具返回和重试全部必须同时具备容量上限与生命周期。**

## 3. LLM 响应慢导致整条链路超时，分层超时和熔断策略是什么？

**面试结论：由入口总 Deadline 统一分配时间预算，各层超时必须小于上游剩余预算；熔断器按“提供商 × 模型 × 区域”隔离，打开后快速失败并走降级，不能让每层各自重试到超时。**

一套完整设计包含五层：

1. **入口总超时**：根据用户 SLO 设总 Deadline，例如交互请求 15 秒，同时预留网关回包和降级所需时间，不能把 15 秒全部交给 LLM。
2. **阶段超时**：排队、检索、重排、LLM 建连、首 Token、Token 间空闲、完整生成、单个工具都要独立设置。流式接口尤其要区分“首 Token 超时”和“流中断超时”。
3. **剩余预算传播**：传递绝对 Deadline 和取消信号，而不是每一层重新获得一个完整的 10 秒。开始下一步前检查剩余预算，不够就提前降级。
4. **受控重试**：只重试 429、连接失败、部分 5xx 等瞬时错误；指数退避加随机抖动，设置最大次数和全局重试预算，并且只允许一个层级负责重试。非幂等写操作没有幂等键就不能自动重试。
5. **断路器**：滚动窗口内超时率、失败率或慢调用比例超过阈值后由 Closed 进入 Open；Open 状态快速失败；冷却后只放少量探测请求进入 Half-open，成功后再恢复。

熔断不能只按供应商做一个全局开关，否则某个模型或区域异常会误伤所有流量。熔断后的降级顺序可以是：同能力备用模型 → 降低最大输出或减少非关键步骤 → 返回可信缓存或部分结果 → 转异步任务 → 明确告知用户稍后重试。

降低超时本身还要做链路优化：缩短 Prompt、限制输出 Token、使用低延迟模型、并行独立检索、连接复用、预热、减少 Agent 循环轮次并尽早流式返回。核心指标不是一个“LLM 耗时”，而是 **排队时间、TTFT、TPOT、完整生成时间、各阶段 P95/P99、超时率、熔断次数和降级成功率**。

## 4. 如何解决 LLM 接口限流？

**面试结论：把供应商的 RPM、TPM 和并发限制转换为本地准入控制，先排队和公平调度，再做有预算的重试、降级和扩容；不能等收到 429 后再处理。**

工程上通常采用以下组合：

- **分布式 Token Bucket/Leaky Bucket**：分别管理请求数和 Token 数；请求前按预计输入加最大输出预占 Token，完成后按实际用量结算。
- **并发信号量**：限制同一提供商、模型、租户和优先级的 In-flight 请求，防止并发限制先于 RPM/TPM 被打满。
- **有界优先级队列**：在线请求高于离线批任务；同一租户设置配额或加权公平队列，避免大客户独占额度。超过最大排队时间就快速失败或降级。
- **自适应并发**：根据 429、延迟和服务端 Rate-limit Header 动态降低并发，恢复时缓慢探测，避免固定并发在供应商抖动时持续撞限。
- **正确重试**：遵守 `Retry-After`，指数退避加 Jitter；设置重试预算和最大队列年龄，防止“限流—重试—更严重限流”的雪崩。

从需求侧还可以通过 Prompt/响应缓存、请求合并、缩短上下文、减少不必要的反思调用、批处理 Embedding、简单任务改走小模型来降低配额消耗。容量确实不足时，再申请更高配额、购买预留吞吐，或路由到经过评测的备用模型和供应商。

多 API Key 只能用于合法隔离不同项目或租户的配额，不能用来绕过供应商限制。需要持续观测 **配额利用率、429 率、排队时长、丢弃率、重试放大系数、每租户使用量和实际/预估 Token 偏差**。

## 5. 检索、工具、多轮推理链路很长，如何降低 P95 RT？

**面试结论：先用 Trace 找到关键路径，再同时减少串行轮次、压缩每一步耗时并治理长尾；优化目标是 P95，不是平均值，也不是简单地把所有步骤都并发。**

第一步是把端到端 RT 拆成：准入排队、模型路由、检索、重排、LLM 首 Token/生成、工具、Agent 空转和网络耗时。注意，链路 P95 不能通过简单相加各节点 P95 得到，必须从同一批端到端 Trace 分析真正的关键路径。

优化顺序通常是：

1. **减少模型往返次数**：把细粒度 API 合并成面向任务的工具，例如一次返回工单、客户和订单上下文；固定流程用代码 Workflow，不让模型每一步重新决定；设置循环、重规划和工具调用上限。
2. **把串行链路改成 DAG**：相互独立的多路检索、权限校验、用户画像读取和只读工具并发执行；有依赖的步骤仍按拓扑顺序执行。可在意图置信度足够高时预取，但要控制无效请求成本。
3. **缩短 LLM 阶段**：只给相关上下文，延迟加载工具 Schema；路由、分类、抽取走小模型；限制输出长度；选择低 TTFT 模型并流式返回。
4. **优化检索与工具**：查询 Embedding/检索结果缓存、Metadata 预过滤、合适的 ANN 参数、连接复用、批量查询和避免 N+1 调用。
5. **治理长尾**：每阶段有超时和剩余预算；对幂等只读请求可以做受控 Hedging，拿到一个成功结果后取消其余请求；慢依赖熔断并走备用实例或降级结果。
6. **区分交互与长任务**：超出同步 SLO 的研究或批处理立即返回 `task_id`，后台执行并持续推送进度；不要让 HTTP 连接承担几十分钟任务。

优化后必须同时回归任务成功率、答案质量和成本。把 8 秒降到 3 秒却让检索召回率下降或调用量翻倍，不是有效优化。推荐设立 **端到端 P95、TTFT P95、关键路径各阶段占比、平均 Agent 步数、无效工具调用率和超时降级成功率**。

## 6. 生产环境完整的 Agent 缓存体系是什么？哪些能缓存，哪些不能？

**面试结论：缓存不是一个 Redis，而是从静态 Prompt 到检索、模型、工具和工作流结果的分层体系；能否缓存取决于确定性、时效性、副作用和安全边界。**

常见缓存层如下：

| 层级 | 可缓存数据 | 关键要求 |
| --- | --- | --- |
| 进程内 LRU | 模型配置、静态 Schema、热点小对象 | 小容量、短 TTL，允许实例间不一致 |
| 分布式缓存 | 会话派生状态、热点元数据、限流计数 | 租户隔离、过期和一致性策略 |
| Prompt Prefix Cache | 稳定系统提示词、工具 Schema、公共长前缀 | 稳定内容放前面，动态内容放后面 |
| 精确响应缓存 | 完全相同且可复用的模型请求 | Key 包含模型、参数和模板版本 |
| 语义缓存 | 意图相近、容许复用的低风险问答 | 相似阈值、质量评估、作用域和短 TTL |
| RAG 缓存 | 文档解析、Chunk、Embedding、查询向量、检索结果 | 绑定语料库和索引版本；更新后失效 |
| 工具结果缓存 | 天气、产品目录、只读配置等允许陈旧的数据 | 按业务定义 TTL，不能隐藏权限检查 |
| 工作流节点缓存 | 输入确定且无副作用的中间节点或已完成任务结果 | 输入 Hash、节点版本、幂等和完整状态 |

一个可靠 Cache Key 至少考虑：`tenant/user/security_scope + model/version + prompt_template_version + tool_schema_version + corpus/index_version + locale + sampling_params + normalized_input`。必须有 TTL、容量上限、主动失效、缓存击穿保护和可观测命中率。

以下数据不能缓存，或只能在非常严格的条件下短暂缓存：

- 支付、删除、发消息、创建工单等有副作用的调用本身；它们需要的是幂等记录，不是结果复用。
- 强实时库存、余额、权限、订单状态等，除非业务明确接受最大陈旧时间，并且权限撤销能够立即生效。
- 含个人信息、企业机密或租户数据的结果，禁止放进跨用户、跨租户的共享 Key。
- 超时、半截流、未通过校验的答案和未知完成状态，不能当作成功结果缓存。
- 高随机性生成或依赖“当前时间、当前会话、当前外部状态”的结果，不能盲目做语义缓存。

缓存永远不能绕过鉴权。检索结果即使命中缓存，也要重新确认当前主体仍有访问资格。生产上还要监控 **命中率、节省 Token/RT、陈旧命中率、错误复用率、击穿次数和跨租户安全测试**。

## 7. Agent 的 Token 成本持续增长，有哪些降本手段？

**面试结论：先按“每个成功任务”拆出 Token 花在哪里，再从模型、上下文、工作流和缓存四层优化；只换便宜模型通常会用更多重试把成本补回来。**

第一步建立成本账本：按租户、场景、模型、工作流节点记录输入 Token、输出 Token、缓存 Token、调用次数、重试、Agent 步数和最终是否成功。核心指标应是 **Cost per Successful Task**，而不是单次调用价格。

主要手段包括：

1. **上下文治理**：相关内容按需检索；旧对话做结构化摘要；大工具结果写对象存储，只在上下文保留摘要和引用；删除重复系统提示、无关示例和历史错误轨迹。
2. **模型分级**：分类、抽取、改写、路由走小模型；复杂推理或高风险任务才升级大模型；用离线评测确定升级阈值。
3. **工作流收敛**：固定规则代码化；设置最大步数、最大重试、最大反思轮次和 Token 预算；检测重复工具调用与无进展循环；不要默认每个回答都再调用一个 Judge。
4. **工具和 RAG 瘦身**：只暴露当前意图需要的工具；工具返回精简字段；调整 Top-K 后用重排选少量高质量 Chunk，而不是把几十段原文都塞给模型。
5. **限制输出**：结构化输出、明确长度、设置 `max_output_tokens`，能返回 ID/枚举就不要让模型写长篇解释。
6. **缓存与复用**：使用稳定 Prompt 前缀缓存、精确/语义缓存、查询向量缓存、任务结果缓存；对同时到达的相同请求做 Singleflight 合并。
7. **批量与本地化**：Embedding 和离线任务批处理；稳定高频的小任务可用蒸馏、微调或自托管小模型，但要把算力、运维和质量回归成本算进去。

最终用一条成本—质量曲线做决策：在任务成功率、安全和 P95 SLO 不下降的约束下最小化成本。另设每租户、每会话和每任务预算，接近上限时缩短回答、停止非关键步骤、升级人工或明确失败，不能无限消耗。

## 8. 多用户并发时如何工程化实现会话隔离，避免串会话？

**面试结论：用服务端可信身份构造 `tenant_id + user_id + session_id + run_id` 全链路命名空间，状态存储、缓存、向量检索、队列和日志都按这个命名空间隔离；绝不能让全局对象或模型自己决定当前用户。**

关键设计如下：

- `tenant_id/user_id` 来自认证令牌和服务端映射，不能相信客户端随请求提交的租户 ID。
- 会话表使用复合主键或 Row-Level Security；所有 Repository 方法强制接收租户上下文，禁止存在“只按 `session_id` 查询”的接口。
- 向量库使用 Namespace/Partition 加服务端 Metadata Filter；对象存储路径、Redis Key、消息队列和搜索索引同样携带租户维度。
- 每个请求创建独立 Agent State，不在单例 Agent 上保存 `current_user`、历史消息或当前工具结果。连接池只复用连接，不复用请求状态。
- 队列消息要显式携带身份和授权快照的引用；消费者重新建立安全上下文，不能依赖线程本地变量或上一个任务残留的数据。

同一会话的两个请求还存在写入顺序问题。通常有两种方案：

1. **单写者/会话 Actor**：同一 `session_id` 串行执行，简单可靠，适合对话轮次有严格顺序的场景。
2. **乐观并发控制**：状态带 `revision`，更新时 Compare-And-Swap；冲突后重读、合并或拒绝。适合允许分支任务的场景。

所有写操作还要有 `run_id/step_id/idempotency_key`，防止超时重试产生重复消息或重复副作用。日志和 Trace 需能关联会话，但要脱敏；缓存必须把权限作用域放进 Key。

上线前应做专门的隔离测试：并发创建相同短 ID 的不同租户、随机切换用户、重复投递消息、复用 Worker、撤销权限后读缓存，以及恶意伪造 `tenant_id`。**串会话本质是数据越权，应该按安全事故而不是普通 Bug 处理。**

## 9. 生产环境出现大量异步任务堆积，如何治理任务队列？

**面试结论：先判断是到达速率持续大于消费能力，还是慢依赖、重试风暴、毒任务或热点分区导致的局部堵塞；治理重点是背压、公平调度、幂等消费和可恢复，而不是盲目加 Worker。**

先观测以下指标：生产/消费速率、Queue Age P50/P95、队列深度、执行耗时、成功率、重试次数、DLQ 数、Worker 利用率、下游 429/超时，以及按任务类型和租户的分布。**Queue Age 通常比 Queue Length 更能说明用户等待了多久。**

治理步骤是：

1. **有界准入和背压**：队列、租户和任务类型都有容量；超过阈值后拒绝低优先级任务、转预约执行或通知上游降速。
2. **优先级与公平性**：在线交互、付费高优任务和离线批任务分队列/资源池；采用租户配额或加权公平队列，避免一个租户制造全局饥饿。
3. **按 Lag 扩缩容**：根据 Queue Age、到达速率和处理速率预测需要的 Worker，同时考虑 LLM/数据库等下游容量。下游已经限流时，继续扩 Worker 只会制造更多 429。
4. **可靠消费**：采用至少一次投递加幂等消费者；任务领取使用 Lease/Visibility Timeout、心跳和 Fencing Token，Worker 崩溃后可以重新领取，旧 Worker 恢复后也不能覆盖新结果。只有结果持久化成功后才能 ACK。
5. **重试分流**：指数退避加 Jitter，放入延迟队列；限制最大次数和全局重试预算；确定性错误直接进入 DLQ，不要占用主队列。
6. **毒任务治理**：记录最后错误、输入版本和尝试次数；提供隔离、人工修复、重放和丢弃工具，不能让单个任务无限阻塞分区。
7. **拆分与批处理**：大任务切成有检查点的小 Chunk；I/O 任务与 CPU 任务使用不同 Worker Pool；相同模型和 Embedding 请求尽量批量执行。

容量判断可以用一个简单关系：当平均到达速率 `λ` 长期大于有效处理速率 `μ`，队列一定发散。扩容只是提高 `μ`，若根因是重试放大或下游限流，应先减少无效到达量。

## 10. 小模型便宜但推理弱，大模型准确但昂贵，如何平衡？

**面试结论：不要固定按比例分流，而要按任务复杂度、不确定性和风险做分级路由；采用“小模型先做、校验失败再升级”的级联，但升级条件必须由评测校准。**

典型策略是：

- 规则匹配、意图分类、字段抽取、查询改写和低风险 FAQ 走小模型。
- 多约束规划、复杂工具选择、长上下文综合、高价值或不可逆操作走大模型，必要时人工确认。
- 小模型输出经过 Schema、业务规则、检索证据或专用评估器校验；置信度低、格式失败、证据冲突、风险等级高时升级大模型。
- 一个任务可按阶段混用模型：小模型做路由和压缩，大模型只处理真正需要推理的核心节点，而不是整条链路统一用一个模型。

“让小模型自报置信度”通常不可靠。置信度应通过带标签数据做校准，并结合意图、输入长度、工具数量、检索得分、历史成功率和业务风险。大模型复核小模型也不一定省钱：如果几乎每次都复核，就变成两次调用；应在离线评测中比较级联后的整体成功率、P95 和每成功任务成本。

可以先算一笔期望账：`级联成本 = 小模型成本 + 升级概率 × 大模型成本`。如果升级率很高，级联可能比直接使用大模型更慢、更贵。

最终优化问题是：**在准确率、安全率和时延 SLO 的约束下，最小化每个成功任务成本。** 每类场景都应有单独阈值、回归集和回退开关，不能用全局经验值代替数据。

## 11. 生产环境如何做模型调度？

**面试结论：模型调度是一个控制平面问题：先用能力、合规和上下文长度做硬过滤，再按质量、实时延迟、成本、配额和健康度动态打分，并通过版本治理保证可回滚。**

完整调度器通常包含：

1. **模型注册表**：记录模型/版本的上下文窗口、工具调用、结构化输出、多模态、数据区域、价格、TTFT、吞吐、配额和已知限制。
2. **硬约束过滤**：数据驻留、敏感级别、客户白名单、所需上下文、工具能力和输出 Schema 不满足的模型直接排除，不能仅因便宜就选用。
3. **任务路由**：根据意图、复杂度、预计 Token、风险等级、租户 SLA 和剩余预算选择模型层级。
4. **运行时负载均衡**：综合 In-flight Token、排队时间、近期 P95、429 和熔断状态，做延迟感知/最少负载调度，而不只是轮询。
5. **Fallback Chain**：备用模型必须验证工具协议、JSON Schema、上下文长度、安全和语义质量兼容；不是所有 OpenAI-compatible 接口都具有相同能力。
6. **发布治理**：模型版本固定，不静默跟随 `latest`；新版本先离线回归，再 Shadow、Canary、逐步放量，SLO 或质量越界自动回滚。

大小模型平衡回答的是“什么任务值得用什么能力”，模型调度回答的是“在当前配额、延迟、故障和版本状态下，具体把这一次请求发到哪里”。核心观测是 **各路由命中率、任务成功率、质量分、TTFT/P95、429、Fallback 率、单位成功成本和版本回归差异**。

## 12. 百万级知识库的向量检索 RT 越来越高，如何优化？

**面试结论：先拆分 Embedding、过滤、ANN 搜索、取原文、重排和网络耗时，再通过索引选型与调参、分区过滤、冷热分层和两阶段检索降低候选规模；任何 RT 优化都必须同时验证 Recall。**

常见优化路径如下：

1. **建立分段指标**：不要只看总 RT。区分查询向量生成、Metadata Filter、ANN、回表、Rerank、跨区网络和序列化，并看 P95/P99、扫描候选数和缓存命中。
2. **从精确搜索转 ANN**：根据内存和更新模式选择 HNSW、IVF/IVF-PQ、DiskANN 等；调节 `efSearch`、`nprobe`、图连接数和量化参数，在 Recall—RT—内存之间做基准测试。
3. **先缩小搜索空间**：按租户、业务域、语言、时间或权限做物理分区/Shard，查询时执行有索引的 Metadata 预过滤；避免在一个全局百万库中先召回再做权限过滤。
4. **控制数据质量和规模**：去重，使用合理 Chunk 大小和重叠；清理 Tombstone、定期 Compact；评估更低维 Embedding 和向量量化，避免无效高维向量占满内存。
5. **两阶段检索**：ANN/关键词混合检索召回适量候选，再用 Reranker 选最终少量 Top-K。Top-K 越大并不等于效果越好，还会提高重排和 LLM 成本。
6. **缓存与热数据**：缓存查询 Embedding 和允许复用的检索结果；热点索引常驻内存、冷数据落盘；实例启动后预热，避免发布后的冷查询尖峰。
7. **读写分离和水平扩展**：批量异步写入与查询节点隔离；热点 Shard 加只读副本；均衡分片，避免某个大租户或热点分区拖慢全局。

最终用真实问题集绘制 Recall@K/NDCG、P95、内存和成本曲线，再选参数。只把 `efSearch` 或 `nprobe` 调低虽然能让 RT 变快，却可能让 RAG 在不报错的情况下悄悄答错，这是最危险的“优化”。

## 13. Agent 服务如何设计启动和停止？

**面试结论：启动时先准备依赖和状态，最后接流量；停止时先摘流量和停止领取新任务，再在截止时间内排空、检查点和释放资源。Liveness 与 Readiness 必须分开。**

推荐启动顺序：

1. 加载并校验配置、证书、密钥和模型路由规则，错误时 Fail Fast。
2. 初始化日志、指标和 Trace，使后续启动失败也可观测。
3. 建立数据库、缓存、队列、模型和工具客户端，执行有上限的健康探测。
4. 加载 Prompt/策略版本，预热连接、热点缓存、Tokenizer、索引或本地模型。
5. 启动后台消费者和定时任务，但要确保重复启动不会重复执行单例任务。
6. 所有必要能力可用后才把 Readiness 置为 Ready，开始接收流量。

数据库变更最好由独立发布步骤执行，避免多个实例启动时并发执行危险迁移。Startup Probe 表示是否仍在初始化，Liveness 只说明进程是否需要重启，Readiness 表示实例是否能安全接流量；依赖短暂抖动通常应摘除流量，而不是立刻反复重启进程。

推荐停止顺序：

1. 收到终止信号后立刻置为 Not Ready，让负载均衡停止分配新请求。
2. 停止领取新队列任务、定时任务和新 Agent Run。
3. 给正在执行的短请求一个 Drain Deadline；向整条调用链传播取消信号。
4. 长任务写入检查点并释放 Lease，或安全地重新入队；有副作用的步骤先确认最终状态。
5. 完成流式响应的收尾，刷新必要日志/Trace/计费记录，关闭连接池、线程池和文件。
6. 超过终止宽限期后才强制退出，并记录未完成任务以便恢复。

启停流程必须幂等，并通过“正在流式输出时发布、正在执行工具写操作时宕机、队列任务执行一半被终止”等故障注入验证。

## 14. 如何避免发布期间用户体验报错？

**面试结论：无损发布依赖混合版本兼容、就绪探针、流量渐进、连接排空和自动回滚；滚动发布本身并不自动等于无损。**

关键措施包括：

- 使用 Rolling、Canary 或 Blue-Green；先小流量验证真实 SLO，再逐步放量。
- `maxUnavailable=0` 或保持足够冗余，并为发布期间的双版本和连接排空预留容量。
- 新实例完成连接、Prompt、模型和索引预热后才 Ready；旧实例先 Not Ready，再执行 `preStop` 和优雅 Drain。
- 会话状态放到外部持久化存储，实例无状态化；长连接/流式请求要允许旧实例继续完成，或提供可恢复的 `run_id/resume_token`。
- API、消息和工作流状态必须前后兼容。数据库采用 **Expand—Migrate—Contract**：先新增兼容字段，完成双读/双写或回填，最后再删除旧字段。
- Prompt、工具 Schema、模型和工作流版本要一起标记；旧任务恢复时仍能找到兼容执行器。
- 高风险功能用 Feature Flag 控制，支持按租户开关和一键回退。
- 以错误率、P95、超时、任务成功率、质量回归和成本异常作为自动暂停/回滚条件，而不是只看容器是否存活。

上线前做一次混合版本演练：新旧实例同时读写、消息重复投递、长任务跨版本恢复、缓存 Key 变化、权限撤销和数据库回滚。用户看到的报错很多并非部署中断，而是新旧版本对同一状态理解不同。

## 15. 长任务执行失败后不想从头跑，如何设计？

**面试结论：把长任务实现为持久化工作流/状态机，在有意义的步骤边界原子提交检查点；恢复时从最后一个已确认步骤继续，所有外部副作用都要幂等或可对账。**

每个 Run 至少保存：

```text
run_id
workflow_version
step_id / step_version
input_hash
status: pending | running | succeeded | failed | waiting
attempt
structured_state
output_artifact_uri
lease_owner / lease_expire_at
created_at / updated_at
```

具体做法是：

1. 把任务切成可重放、耗时适中的步骤，步骤完成后再原子写入状态和产物引用。不要只在内存里更新“已完成”。
2. 使用 `run_id + step_id` 作为幂等键。数据库写入、消息发送、支付等副作用由幂等 API 或本地去重表保护。
3. 对“请求超时但第三方可能已经执行”的不确定状态，先用幂等键查询/对账，不能直接再调一次。
4. Worker 通过 Lease、心跳和 Fencing Token 持有任务；宕机后 Reaper 回收过期 Lease，新 Worker 从最后检查点继续，旧 Worker 即使恢复也不能提交过期结果。
5. 大型中间结果写对象存储，状态库只存结构化摘要、Hash 和 URI；不要持久化模型的隐藏思维链。
6. 不可逆的多系统事务采用 Saga：为已完成步骤设计补偿动作；无法自动补偿时进入人工处理状态。
7. 用 Transactional Outbox/Inbox 解决“业务状态已提交但消息未发送”或“消息已收到但结果未落库”的双写问题。
8. 工作流和 Prompt 必须版本化。新版本发布后，旧 Run 是由旧执行器继续，还是经过显式迁移，不能临时猜测。

这套设计的语义通常是 **At-least-once 执行 + 幂等效果**，不要轻易宣称端到端 Exactly-once。测试时要在每个步骤提交前后强制杀进程，验证不会丢步骤、重复扣费或从头开始。

## 16. 哪些逻辑必须由工程代码控制，不能交给 LLM 自主判断？

**面试结论：凡是必须正确、可重复、可审计，或失败会产生安全、资金、权限和不可逆影响的逻辑，都必须由确定性代码和策略引擎控制；LLM 只负责模糊理解与候选建议。**

这里的“硬编码”并不是把规则散落成大量 `if/else`，而是要求它们由可测试、可审计、可版本化的代码、配置或策略引擎确定性执行。

必须代码化的典型逻辑包括：

- 身份认证、授权、租户隔离、数据可见范围和密钥访问。
- 支付、退款、删除、发信、部署等高风险操作的额度、审批、Dry-run、幂等和事务。
- 参数 Schema、类型、枚举、范围、资源存在性和业务前置条件校验。
- 状态机合法转移，例如订单不能从“已退款”回到“待支付”。
- 超时、重试、熔断、并发、队列、最大步数、Token/成本预算和终止条件。
- 隐私脱敏、内容安全、合规、数据驻留、审计留痕和保留/删除策略。
- 确定性的金额、时间、配额和业务公式计算。
- 结果验收中可通过代码、数据库状态或测试明确判断的部分。

不能让 LLM 决定自己的权限、预算、是否成功、是否需要绕过审批，以及“失败后要不要再试一次”。模型适合做意图分类、自然语言抽取、检索词生成、候选计划、草稿和相关性排序，但它的输出必须经过 Schema、权限和业务规则验证。

一个实用判断标准是：**如果同一输入在审计时必须得到同一结论，或错误结论不能接受，就不要把最终决定权交给 LLM。**

## 17. 如何评定 Agent 的性能、成本和稳定性？核心指标有哪些？

**面试结论：指标必须覆盖“结果、过程、资源和业务”四层，并统一落到任务成功率、P95/P99、每成功任务成本和 SLO；只看模型调用成功率没有意义。**

| 维度 | 核心指标 |
| --- | --- |
| 结果质量 | 任务完成率、答案正确率、Groundedness/引用正确率、业务规则通过率、人工接管率、用户重试/纠正率 |
| Agent 过程 | 平均/P95 步数、工具选择正确率、参数校验失败率、工具成功率、循环率、重规划率、无进展终止率、检查点恢复成功率 |
| 性能 | E2E P50/P95/P99、TTFT、TPOT、各阶段关键路径耗时、队列等待、吞吐、并发、流式中断率 |
| 成本 | 输入/输出/缓存 Token、模型/Embedding/Rerank/工具/存储成本、重试浪费、每任务成本、每成功任务成本、每租户预算利用率 |
| 稳定性 | 可用性、错误/超时/429 率、熔断和降级率、Crash/OOM、GC、连接池、CPU/内存、队列年龄、恢复时间 MTTR |
| 安全与合规 | 越权拦截、跨租户泄漏、提示注入成功率、敏感数据外发、危险操作未确认率、审计完整率 |
| 业务 | 解决率、转化率、处理时长、人工节省、用户满意度，以及错误结果造成的业务损失 |

观测链路要以 `trace_id/run_id` 串联入口、路由、Prompt/模型版本、检索、工具、队列和最终状态。高基数 ID 放在 Trace/日志，不要直接变成 Prometheus Label。Prompt 和工具结果需按数据等级脱敏或只记录 Hash/摘要。

评估分三层：单步工具与参数、整条 Agent 轨迹、端到端最终状态。线上指标负责发现真实分布问题，离线回归集负责比较 Prompt/模型/工作流版本。最终应该定义清晰 SLO，例如“任务成功率 ≥ 98%，P95 ≤ 8 秒，单个成功任务成本 ≤ 0.05 美元”，并为错误率和成本设置预算。

## 18. 批量处理时 CPU 和内存瞬时打满，如何解决？

**面试结论：核心是有界并发和按资源加权的调度，配合分块、流式和在线/离线资源隔离；自动扩容只能扩大容量，不能替代背压。**

治理方法如下：

1. **Worker Pool + Semaphore**：禁止每条数据创建一个无界协程。并发度根据 CPU、内存和下游额度设置，并能动态下调。
2. **加权准入**：任务大小差异大时不能只数 Job。按预计 Token、文档字节数、图片像素或向量数预估资源，使用 Weighted Semaphore 和内存预算。
3. **分块与流式**：分页读取、分块解析、流式写结果，处理完即释放；不要把整批文档、全部 Embedding 和最终结果同时放在内存中。
4. **拆分资源池**：CPU 密集解析、I/O 调用、GPU 推理使用不同队列和 Worker；离线批任务与在线请求隔离配额、实例或节点，保证在线 SLO。
5. **减少内存放大**：避免反复 JSON 序列化和大数组复制；中间产物放对象存储；复用合理大小的 Buffer，但防止对象池长期保留超大 Buffer。
6. **自适应批大小**：Embedding/推理批处理能提高吞吐，但 Batch 太大会抬高峰值内存和尾延迟；根据资源水位动态调整。
7. **资源水位保护**：CPU、Heap、GC、队列年龄超过阈值时暂停领取、降低并发或丢弃低优任务，而不是等 OOM Killer。

排查时做 CPU/Heap Profile，区分业务计算、序列化、GC、锁争用和大对象分配；结合每种任务的 CPU 秒、峰值内存、处理时长建立容量模型。批任务也要有检查点，缩小批次后可以从失败 Chunk 继续，而不是重跑整批。

## 19. 多轮对话上下文越来越大、越来越冗余，如何工程化治理？

**面试结论：把原始 Transcript、当前工作状态和长期记忆分开管理；上下文只装完成当前一步所需的信息，旧对话摘要化，大结果外置，相关记忆按需检索。**

推荐把上下文分成四层：

1. **稳定指令层**：系统 Prompt、策略和少量工具 Schema，版本化并尽量利用 Prefix Cache。
2. **当前工作状态**：目标、约束、已确认事实、计划、当前步骤、未解决问题和预算，使用结构化字段而不是从长对话重新推断。
3. **最近窗口**：保留最近若干轮原文，窗口按 Token 预算而不是固定消息条数截取。
4. **长期资料**：历史消息、工具原文、附件和长期记忆保存在外部存储，通过关键词、向量、时间和权限过滤按需取回。

当上下文接近预算时，把旧内容压缩成包含“用户目标、关键事实、明确约束、已做决定、引用来源、未完成事项”的结构化摘要。工具返回的大网页、日志和文档写入对象存储，只在上下文保留短摘要、URI、Hash 和可引用片段。重复 Chunk、相同错误和无效尝试要去重。

摘要也会丢信息，因此应保留原始事实来源和版本；关键数字、权限、用户明确更正不能只靠自由文本摘要。避免一轮轮“摘要上次摘要”造成语义漂移，可以定期从结构化状态和原始来源重新生成。用户新信息与旧记忆冲突时要有更新时间、来源和覆盖规则。

为系统 Prompt、最近对话、检索文档、工具返回和输出分别设置 Token 配额，并观测 **上下文 Token、压缩率、检索命中、摘要后任务成功率、被截断关键事实率和每轮成本**。

## 20. 第三方 RRM 接口不稳定、抖动并且超时，如何保证高可用？

> 这里把题目中的 RRM 按“第三方模型、重排模型或工具接口”理解；无论具体是 LLM、Reranker 还是 Reward Model，依赖治理原则相同。

**面试结论：通过超时、重试预算、熔断、隔舱和多实现降级把第三方故障限制在单一故障域内，同时保证请求幂等和结果语义兼容。**

完整方案包括：

- **统一 Adapter/Gateway**：屏蔽不同供应商鉴权、请求和响应格式，对上层暴露稳定契约；保留供应商错误码和请求 ID 便于对账。
- **分层超时与取消**：连接、首字节、空闲和总调用分别限时，并受入口剩余 Deadline 约束。
- **有限重试**：仅对瞬时且幂等错误重试，指数退避加 Jitter，遵守 `Retry-After`；单请求和全局都有重试预算。
- **断路器与隔舱**：按供应商、模型、区域建立独立熔断器；每个依赖使用独立线程池/连接池/信号量，防止一个慢依赖占满整个 Agent 服务。
- **健康感知路由**：根据实时 P95、超时、429 和熔断状态切换备用供应商或本地模型；持续用小流量探测恢复。
- **降级策略**：使用可信短期缓存、跳过非关键 Rerank、降低候选数、返回部分结果、改成异步，或明确提示当前能力受限。
- **受控 Hedging**：只对高尾延迟、幂等只读且价值足够的请求，在超过历史高分位延迟后发一个备用请求；一个成功后立即取消其余，避免常态双倍成本。

备用接口必须做能力和质量兼容测试：上下文长度、工具调用、结构化输出、Embedding 维度或 Rerank 分数分布可能不同，不能“能返回 200 就算可替换”。对外部写操作使用幂等键并对不确定结果进行查询确认。

还要设置依赖 SLO、合成探测和故障演练，观测供应商 P95/P99、超时、429、熔断、Fallback 成功率、重试放大和降级后的业务成功率。多供应商只能降低单点风险，不能替代本地的有界设计。

## 21. 企业级 Agent 如何做权限、数据隔离和多租户设计？

**面试结论：身份由企业 IdP 建立，权限由确定性策略引擎执行，租户上下文贯穿模型、RAG、工具、缓存、队列和审计；LLM 永远不能充当授权系统。**

建议分层落地：

1. **认证**：接入 OIDC/SAML/企业 SSO；用户、服务和 Agent 使用不同身份，服务间使用短期凭证，不把长期密钥放进 Prompt。
2. **授权**：RBAC 管角色，ABAC/ReBAC 表达资源归属、部门、数据等级和委托关系。每一次检索和工具调用都由服务端 Policy Enforcement Point 校验主体、动作、资源和上下文。
3. **数据隔离**：
   - 普通租户可共享数据库但必须有 `tenant_id`、复合主键和数据库 RLS。
   - 更高隔离可采用独立 Schema、数据库、索引或存储桶。
   - 高合规客户可以独立账号/VPC、区域和 KMS Key。
   隔离等级由风险和成本决定，但上层访问接口保持一致。
4. **RAG 权限**：权限条件必须在向量/关键词查询阶段前置过滤，召回后再做一次防御性校验；不能先检索全部机密文档，再要求模型“不要泄漏”。
5. **工具委托**：Agent 使用用户授权范围内的短期 Token 调工具；高危工具 Allowlist、最小权限、审批和额度控制，禁止所有 Agent 共用一个超级管理员凭证。
6. **全链路分区**：缓存 Key、队列、对象存储、工作流状态、日志和备份都包含租户作用域；监控告警避免直接暴露敏感内容。
7. **数据治理**：传输/静态加密、字段脱敏、保留期限、删除权、区域驻留、模型供应商“不用于训练”配置和不可篡改审计。

Prompt Injection 要作为权限攻击处理：检索到的文档和网页是不可信数据，不能改变系统策略或扩大工具权限。上线前需要自动化跨租户渗透测试、伪造身份测试、缓存污染测试和权限撤销实时性测试。

## 22. 从 0 搭建生产可用的企业级 Agent 平台，核心工程顺序是什么？

**面试结论：先定义可评测的业务闭环和安全边界，再建立确定性工作流、可靠状态和可观测性，最后才做性能优化、模型调度和多 Agent；顺序反过来会把不可控复杂度提前放大。**

推荐按以下阶段推进：

### 阶段 0：定义价值、风险和验收标准

- 选择一个边界清晰、可回放的场景，定义输入、输出和“不做什么”。
- 建立 30–100 条真实样本和失败样本，定义任务成功率、质量、安全、P95 和单任务成本目标。
- 做数据分级、威胁建模和人工接管规则，明确哪些动作不可逆。

**退出条件：** 不依赖“看起来不错”，能用测试、规则或人工 Rubric 判断成功。

### 阶段 1：打通最小确定性闭环

- 建立 API Gateway、认证和租户上下文。
- 使用单模型、单 Agent 或固定 Workflow，只接少量只读工具。
- 工具采用严格 Schema、最小权限和运行时参数校验。
- Prompt、模型、工具和数据版本全部可追踪。

**退出条件：** 在开发环境稳定完成核心任务，并能解释每次失败发生在哪一步。

### 阶段 2：补齐生产可靠性底座

- 引入持久化会话/工作流状态、`run_id/step_id`、幂等、检查点和取消。
- 建立分层超时、有限重试、熔断、隔舱、有界并发、队列背压和 DLQ。
- 高风险写操作增加 Dry-run、审批、对账和补偿。
- 实现优雅启停、Readiness、无损发布和版本兼容。

**退出条件：** 依赖超时、重复消息、进程宕机和发布中的任务都能恢复，不造成重复副作用。

### 阶段 3：建立可观测、评测和安全闭环

- 用统一 Trace 串联模型、检索、工具和队列；建立性能、成本、质量和安全看板。
- 所有 Prompt/模型/工具变更运行离线回归，发布时 Shadow/Canary 和自动回滚。
- 加入越权、Prompt Injection、敏感数据外发和跨租户测试。
- 建立告警、值班、Runbook、故障复盘和成本预算。

**退出条件：** 线上问题可以定位到具体租户、版本和步骤，并能量化变更是否真的更好。

### 阶段 4：按瓶颈做规模化优化

- 增加分层缓存、RAG 索引优化、模型路由、限流、公平调度和批处理。
- 通过小模型级联、上下文治理和工具合并降低 P95 与每成功任务成本。
- 做容量模型、压测、Soak Test、故障注入、多区域备份与恢复演练。

**退出条件：** 在目标峰值流量和依赖故障下仍满足 SLO，且成本随业务量可预测。

### 阶段 5：有证据地增加自主性

- 只有固定 Workflow 无法覆盖动态路径时才扩大 Agent 决策权。
- 只有任务可以真正并行或需要独立上下文时才引入多 Agent。
- 每增加一个模型决策、工具或 Agent，都要同步增加契约、预算、终止条件和回归用例。

一套平台最终通常包含以下能力面：

```text
接入面：API Gateway / Auth / Tenant Context / Admission Control
执行面：Workflow & Agent Runtime / Durable State / Queue / Scheduler
能力面：Model Gateway / RAG / Tool Gateway / Memory
治理面：Policy / Secrets / Audit / Data Governance
质量面：Tracing / Metrics / Evaluation / Cost / Release Control
```

最重要的工程顺序可以压缩成一句话：**先把成功定义清楚，再让单条链路可靠；先做到可恢复、可观测和安全，再追求更强自主性和更大规模。**

## 面试收尾：贯穿 22 题的统一框架

如果面试官继续追问，可以用下面五条原则把答案收束起来：

1. **所有资源都要有界**：并发、队列、上下文、步骤、重试、时间和 Token。
2. **所有状态都有归属**：请求、会话、租户、工作流和全局状态不能混用。
3. **所有副作用都可恢复**：幂等、检查点、对账、补偿和人工接管。
4. **所有依赖都有故障边界**：超时、熔断、隔舱、降级和背压。
5. **所有优化都以结果验收**：任务成功率、P95、每成功任务成本和安全 SLO 一起看。

生产级 Agent 的核心不是让 LLM 永远不犯错，而是让错误**不会越权、不会无限放大、不会丢失状态，并且能够被发现和恢复**。
