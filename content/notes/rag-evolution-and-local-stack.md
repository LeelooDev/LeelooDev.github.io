RAG 的全称是 Retrieval-Augmented Generation。**检索只是其中一个子系统**；完整工程还包括数据解析、切块与索引、查询理解、证据选择、上下文组织、答案生成、引用校验、拒答和评测。

## RAG 是怎样发展的

| 阶段 | 主要做法 | 优点 | 典型问题 |
| --- | --- | --- | --- |
| 朴素 RAG | 向量 top-k 后直接生成 | 简单、容易验证想法 | 专有名词和精确匹配弱，首次检索失败后无法修正 |
| 混合 RAG | BM25 + 向量召回 + 融合 + 重排 | 同时覆盖关键词与语义 | 仍可能丢失章节背景或跨文档关系 |
| 上下文 RAG | 结构化切块、上下文前缀、父子块扩展 | 片段保留来源与章节语义 | 索引更复杂，需要离线评测 |
| Agentic RAG | Agent 决定是否检索、改写查询和拆分子问题 | 适合模糊问题、多工具和多跳任务 | 延迟与成本不稳定，必须限制循环 |
| Hybrid/Adaptive RAG | 固定流程与 Agent 决策结合，并加入检索/答案校验 | 在可控性与灵活性之间平衡 | 工程和评测成本更高 |
| GraphRAG | 从实体、关系和社区摘要构建图检索 | 擅长全局主题与关系问题 | 建图昂贵，不适合默认替代普通检索 |

[Anthropic 的 Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) 把块级上下文同时加入语义索引和 BM25 索引；[LangChain 的检索文档](https://docs.langchain.com/oss/python/langchain/retrieval) 则把当前架构归纳为 2-Step、Agentic 和二者结合的 Hybrid RAG。趋势不是“只用更大的向量库”，而是让检索更懂结构、让 Agent 能修正失败，同时保留验证环节。

## 2026 年更推荐什么

没有一套对所有语料都最好的“最新方案”。对本地 Markdown 知识库，更可靠的选择是**分层式 Hybrid/Agentic RAG**：

1. 小文件或明确路径直接读原文，不强制经过向量检索。
2. 默认使用 BM25 与向量双路召回，RRF 融合后本地重排。
3. 切块保留标题路径、文件路径和行号；命中子块后按需扩展父章节。
4. Agent 只在证据不足时改写查询、拆分子问题或再次检索，并设置严格轮次上限。
5. 生成前检查证据是否充分，生成后校验每个引用是否真的来自返回证据；不足就拒答。
6. 用真实问题集评估召回率、证据命中、引用正确率、拒答准确率、延迟和资源占用。

这不是把所有步骤都交给 Agent。精确匹配、索引、引用验证和权限控制继续使用确定性代码；只有查询规划和失败恢复使用模型决策。

## 现有方案能不能继续用

**可以，而且已经位于正确的演进路径上。** 当前工程并不是“只有向量 top-k”的朴素 RAG：

| 当前能力 | 所在阶段 | 处理建议 |
| --- | --- | --- |
| SQLite FTS5 / BM25 + CJK unigram | 词法召回 | 保留 |
| `multilingual-e5-small` 本地向量 | 语义召回 | 保留，模型接口可替换 |
| RRF + 本地 reranker | 混合检索与精排 | 保留 |
| Markdown 结构切块 + 精确行号 | 可追溯上下文 | 保留 |
| 四个只读知识工具 | Agentic RAG | 保持契约稳定 |
| 查询改写与子问题拆分 | Agentic RAG | 加预算和效果门槛 |
| 引用证据集与真实问题评测 | 质量控制 | 继续扩充 |

因此不建议为了“更新”而迁移向量数据库、换成云端 File Search，或马上上 GraphRAG。现有 SQLite 方案对单机私有知识库更简单，也能离线工作；先让评测证明瓶颈，再替换管道中的单个组件。

## 下一步落地顺序

1. **父子分段**：子块负责精确召回，父章节负责补齐上下文，同时保留原文行号。
2. **查询路由**：文件名、错误码和 API 名走词法优先；概念问题走混合检索；指定文件直接阅读。
3. **充分性判断**：重排后判断证据是否覆盖问题，不足时最多再检索两轮。
4. **多跳评测**：新增必须跨段落、跨文件组合的题目，以及没有答案时的拒答题。
5. **按需实验 GraphRAG**：只有当大量真实问题都在询问跨文档关系、全局主题或影响路径时，再对一个小语料集做 A/B 测试。微软官方也提示 [GraphRAG 建索引可能消耗大量资源](https://github.com/microsoft/graphrag)，应该从小规模开始。

## 当前决策

**继续使用现有本地混合检索，把下一阶段投入放在父子分段、查询路由、证据充分性和多跳评测。** Agentic RAG 是现有架构的增强方式，不是需要推倒重来的新框架；GraphRAG 暂时列为特定问题的实验项，而不是默认主链路。
